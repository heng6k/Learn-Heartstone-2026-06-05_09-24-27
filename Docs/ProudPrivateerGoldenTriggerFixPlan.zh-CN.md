# 骄傲的私掠者金色触发修正规范

## 目标

修正 5 本海盗随从“骄傲的私掠者（Proud Privateer）”金色版本无法按卡牌文本增加悬赏令施放次数的问题，并为后续代码修改、测试和验收提供唯一规则依据。

本文只定义修正方案，不修改功能代码。

## 卡牌身份与正式描述

用户反馈中的“骄傲的撕掠者”对应项目卡牌“骄傲的私掠者”。

| 项目 | 普通版本 | 金色版本 |
|---|---|---|
| 中文名 | 骄傲的私掠者 | 骄傲的私掠者（金色） |
| 英文名 | Proud Privateer | Proud Privateer（金色） |
| Card ID | `BG33_825` | `BG33_825_G` |
| 酒馆等级 | 5 | 5 |
| 种族 | 海盗 | 海盗 |
| 属性 | 8/8 | 16/16 |
| 中文描述 | 你的悬赏令会施放两次。 | 你的悬赏令会施放三次。 |
| 英文描述 | Your Bounties cast twice. | Your Bounties cast three times. |

项目卡牌数据已经保存了上述普通/金色差异，因此本问题不是卡牌描述数据缺失。

## 实际酒馆战棋规则解释

“施放两次/三次”表示一次正常施放加上额外施放次数：

- 没有骄傲的私掠者：悬赏令总共施放 1 次。
- 1 个普通骄傲的私掠者：额外施放 1 次，总共施放 2 次。
- 1 个金色骄傲的私掠者：额外施放 2 次，总共施放 3 次。

金色版本不能沿用普通版本固定增加 1 次的逻辑，也不能按“普通效果翻倍”错误处理为总共施放 4 次。应直接遵循金色卡牌文本：总共施放 3 次。

同类重复施放光环应按每个在场实例贡献额外次数来累计：普通实例贡献 `+1`，金色实例贡献 `+2`。例如一个普通版本和一个金色版本同时在场时，单张悬赏令应为基础 1 次加额外 3 次，总共施放 4 次。该累计规则可以避免现有“只判断是否存在任意一个实例”导致的多实例丢失。

## 当前实现与根因

当前额外施法次数在 `MatchService` 的酒馆法术重复施放计算中处理。现有逻辑对悬赏令使用：

```csharp
if (IsBountyCardId(spell.CardId) &&
    State.Player.Board.Any(minion => minion.CardId == ObsidianRavagerCardId))
{
    extra += 1;
}
```

这里存在两个直接问题：

1. 只用 `Any(...)` 判断场上是否存在 `BG33_825`，命中后始终只增加 1 次，没有读取 `MinionInstance.Golden`。
2. `Any(...)` 会把多个普通/金色实例压缩成一个布尔值，无法累计每个实例应贡献的额外次数。

因此普通版本恰好表现为文本要求的 2 次，但金色版本仍然只有 2 次，无法达到描述要求的 3 次。

常量名 `ObsidianRavagerCardId` 与其实际指向的 `BG33_825`（Proud Privateer）不一致，容易与真正的 Obsidian Ravager 混淆。后续实现时应同步改为表达实际身份的名称，例如 `ProudPrivateerCardId`；这属于局部可读性修正，不改变存档或卡牌 ID。

## 最小修正方案

只修改悬赏令额外施放次数的计算，不增加新系统或新依赖。

建议把布尔存在判断替换为实例求和：

```csharp
if (IsBountyCardId(spell.CardId))
{
    extra += State.Player.Board
        .Where(minion => minion != null && minion.CardId == ProudPrivateerCardId)
        .Sum(minion => minion.Golden ? 2 : 1);
}
```

实现必须保持以下边界：

- 只对 `IsBountyCardId(...)` 识别出的悬赏令生效。
- 普通酒馆法术不受骄傲的私掠者影响。
- 普通版本贡献一次额外施放，金色版本贡献两次额外施放。
- 多个实例按各自普通/金色状态累计。
- 不通过金色 `CardId` 判断金色身份；项目运行时以普通玩法 `CardId` 配合 `Golden` 标志表示金色随从。
- 不改动悬赏令单次结算内容、选取目标、其它重复施法来源及其叠加顺序。

## 与其它重复施放来源的关系

骄傲的私掠者提供的是额外施放次数，应继续进入现有统一的 `extra` 累计结果，与项目中其它合法重复施放来源相加，而不是单独再次递归调用施法流程。

这样可以保持以下约束：

- 每次额外施放均执行悬赏令自身效果。
- 不重复消费手牌中的原始法术卡。
- 不因额外施放再次计算并指数放大同一批重复施放光环。
- 其它“一回合一次”或需要消费状态的重复施法来源仍由其现有逻辑负责。

## 测试矩阵

后续代码实施至少补充以下专项回归：

| 场景 | 预期总施放次数 |
|---|---:|
| 无骄傲的私掠者，施放一张悬赏令 | 1 |
| 1 个普通骄傲的私掠者 | 2 |
| 1 个金色骄傲的私掠者 | 3 |
| 2 个普通骄傲的私掠者 | 3 |
| 1 个普通 + 1 个金色 | 4 |
| 2 个金色 | 5 |
| 金色骄傲的私掠者，施放非悬赏令酒馆法术 | 1 |

测试应通过可计数的悬赏令效果验证实际结算次数，不能只断言内部 `extra` 数值。若选用属性增益类悬赏令，测试夹具需要固定合法目标并排除其它法术增幅来源。

## 验收标准

- 卡牌详情中普通描述保持“你的悬赏令会施放两次”。
- 卡牌详情中金色描述保持“你的悬赏令会施放三次”。
- 一个普通版本在场时，悬赏令实际结算 2 次。
- 一个金色版本在场时，悬赏令实际结算 3 次，而不是 2 次或 4 次。
- 多个普通/金色实例按照 `普通 +1、金色 +2` 正确累计。
- 非悬赏令法术、悬赏令生成逻辑和其它法术重复来源无回归。

## 根因分析摘要

**错误**：金色骄傲的私掠者在场时，悬赏令没有按金色描述施放三次。

**预期**：基础施放 1 次，金色随从提供额外 2 次，共结算 3 次。

**原因**：当前实现仅用 `Any(...)` 判断是否存在指定随从，并固定执行 `extra += 1`，既忽略 `Golden` 状态，也忽略多个实例。

**修复**：对场上所有骄傲的私掠者实例求和，普通实例贡献 1 次额外施放，金色实例贡献 2 次额外施放。

**预防**：所有普通/金色文本给出不同次数的光环效果，都应使用显式普通/金色权重测试，并至少覆盖一个多实例叠加场景。
