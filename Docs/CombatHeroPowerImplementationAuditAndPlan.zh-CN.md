## 1. 执行摘要

用户反馈“战斗类英雄技能还是不行”并非单个英雄的孤立问题。当前项目已经实现了部分英雄技能，但缺少一个**唯一、双边对称、由战斗引擎主导的英雄技能生命周期**。同类能力目前分散在四条路径中：

1. `HeroEffectEngine.ApplyCombatStartEffects` 在进入战斗引擎前直接修改玩家战斗棋盘；
2. 先向 `TavernState` 写标志，再由 `CombatEngine` 读取，例如塔维什、奥妮克希亚、布鲁坎；
3. `CombatEngine` 内部监听死亡、召唤等事件，例如奥妮克希亚的复仇；
4. 战斗结束后由 `MatchService` 派发奖励或近似补发，例如拉法姆式奖励。

因此，“技能 CardId 在代码中出现”“按钮能使用”“生成了一条日志”“测试检查到 Tavern 标志”都不能证明技能真实可用。真正的可用标准应是：技能进入了本场战斗快照，在正确时点、正确一方、正确目标上触发，并能改变本场棋盘、攻击序列、死亡链、胜负或合法的战后奖励。

本次审计的核心结论如下：

- **确认的结构性根因**：没有统一的 `CombatHeroPowerContract`、双边英雄技能快照和战斗事件归属模型。
- **确认的时序缺口**：英雄开战效果、立即攻击、饰品/任务/随从开战效果分别在多个阶段执行；全局相对顺序没有由同一队列表达。
- **确认的双边缺口**：玩家侧通过 `HeroEffectEngine` 预处理，敌方侧通过另一套 `ApplyOpponentCombatStartHeroPowers` 处理，天然存在行为漂移风险。
- **确认的目标缺口**：需要预先选目标或选模式的英雄技能依赖可变索引、字符串标记或 Tavern 字段，缺少不可变的战斗目标快照和失效规则。
- **确认的测试缺口**：已有局部黑盒和英雄测试不能等价证明全部英雄的真实战斗语义；需要以 replay、事件、最终棋盘、胜负与回写共同验收。
- **不能直接下结论的部分**：不能声称所有战斗英雄技能都坏了。奥拉基尔、伊利丹、塔维什、布鲁坎、奥妮克希亚等已有不同程度实现，但实现层级、双方一致性和时序精度不相同。

建议先完成 P0 统一管线，再逐类迁移。继续逐英雄打补丁会让技能数量越多、回归面越大。

## 4. 当前代码执行链

当前 `MatchService.RunCombatTest` 的主要顺序是：

```text
同步 Tavern 战斗修正
  -> 克隆玩家/敌方棋盘
  -> HeroEffectEngine.ApplyCombatStartEffects（主要是玩家侧）
  -> 创建敌方 Combat Tavern
  -> ApplyOpponentCombatStartHeroPowers（另一条敌方路径）
  -> 玩家/敌方饰品、任务、时光扭曲预处理
  -> CombatEngine.SimulateBasicCombat
       -> ResolveHeroStartOfCombatEffects
       -> 收集 tagged immediate attacks
       -> 执行立即攻击
       -> 饰品开战效果/亡语/光环
       -> 自然攻击循环
       -> 生成结果、事件、奖励
  -> 永久增益回写
  -> 战斗奖励回写
  -> HeroEffectEventType.CombatEnded
  -> 保存死亡历史、任务奖励和清理临时标志
```

### 4.1 已确认的分裂点

`HeroEffectEngine.ApplyCombatStartEffects` 会直接处理奥拉基尔、死亡之翼、塔姆辛、伊利丹、亚煞极、范达尔、德雷克塔尔、泰隆、奥苏玛特等；塔维什、奥妮克希亚、布鲁坎则主要写入 Tavern 标志，稍后由 `CombatEngine` 消费。

这造成三个直接问题：

1. 预处理效果发生在 `CombatEngine` 的 `CombatStarted` 事件之前，replay 无法完整表达其因果链；
2. 玩家与敌方使用不同准备入口，很容易只修复一侧；
3. 所谓“开战时”效果与饰品、任务、随从开战效果没有统一优先级对象，只能依赖调用代码的当前位置。

### 4.2 已经真实接入战斗引擎的例子

- 塔维什：CombatEngine 读取激活标志和目标字段，造成伤害并标记击杀来源；
- 布鲁坎：CombatEngine 按元素执行效果，并为相关衍生亡语保存标记；
- 奥妮克希亚：死亡结算处维护复仇计数、召唤雏龙并加入立即攻击；
- 伊利丹：预处理给边缘随从标记，CombatEngine 收集并执行立即攻击。

这些属于“已有真实战斗行为”，但仍需补齐双方一致性、统一时序、目标失效与 replay 断言，不能简单标记为完全完成。

## 5. 根因分析

### 5.1 症状

- 技能可以选择或显示已激活，但战斗中无效果；
- 玩家侧有效、敌方侧无效，或反之；
- 日志显示触发，但本场棋盘、攻击顺序或胜负没有变化；
- 首次击杀、复仇、战斗中召唤、死亡记录类技能漏触发或重复触发；
- 选定目标在克隆棋盘后丢失，退化成第一个随从；
- 立即攻击后自然攻击指针不符合预期；
- 战后补发奖励掩盖了战斗事件没有正确发生。

### 5.2 五个为什么

1. 为什么技能“不工作”？因为它没有在正确的战斗时点收到完整状态和事件。
2. 为什么收不到？因为技能逻辑分散在 HeroEffectEngine、MatchService、CombatEngine 和战后回写中。
3. 为什么分散会失败？因为没有统一注册、排序、双边上下文、事件所有者和持久化规则。
4. 为什么测试没有阻止？因为部分测试只验证字段、日志或孤立 helper，没有验证完整模拟结果。
5. 为什么逐英雄修复仍反复出现？因为每次补丁只接通一个 CardId，没有先补齐共享生命周期。

### 5.3 根因结论

**主根因：项目缺少权威的、双边对称的战斗英雄技能契约。** 目标选择、开战队列、战斗事件和战后回写没有共享一个带来源、所有者、时点和持久化边界的模型。

### 5.4 排除项

- 不是单纯的数据文本问题：本地和公开卡牌文本能正确识别这些能力；
- 不是单纯的 CardId 缺失：多个 CardId 已在代码中出现；
- 不是只需增加更多 `if (powerId == ...)`：现有问题发生在生命周期和事件层。

## 6. 逐类不足与改进要求

### 6.1 开战时效果

不足：预先直接改棋盘，未统一进入 replay；双方准备路径不同；同一阶段内没有显式优先级；最低/最高属性并列选择规则不统一。

改进：所有开战效果注册为 `CombatStartAction`，携带 `ownerSide`、`sourceCardId`、`priorityBand`、`stableSequence` 和目标解析器。结算前只创建动作，不直接改棋盘。

### 6.2 立即攻击

不足：立即攻击既可能来自标签，也可能由战斗中召唤临时加入；若两侧同时存在，队列顺序和自然攻击方衔接容易出错。

改进：统一 `ImmediateAttackQueue`。每项记录来源、攻击者实例、所有者、入队时点、是否允许攻击者死亡后跳过。执行后由一个规则更新自然攻击指针，而不是各技能自行处理。

### 6.3 战斗中召唤与“有空位时”

不足：只在开战预处理时检查一次空位，无法表达“后来出现空位”；不同召唤入口可能绕过格雷布等修正；复制对象可能取了已修改对象而非规定快照。

改进：引入 `BoardSpaceChanged` 和统一 `SummonResolver`。所有英雄、亡语、饰品、任务、随从生成物都必须通过同一召唤入口。范达尔、德雷克塔尔、泰隆、奥苏玛特注册待触发资格，在每次死亡清理和召唤完成后检查空位。

### 6.4 攻击、击杀、死亡和伤害归属

不足：仅凭“某随从死亡”不能判断是谁击杀；间接伤害、同时死亡、超杀、毒性/烈毒、英雄技能伤害需要来源链。拉法姆要求“你消灭的第一个”，不是“第一个敌方死亡”。

改进：每次伤害和强制消灭生成结构化事件：

```csharp
CombatEvent {
  EventId, Sequence, Type,
  OwnerSide, AffectedSide,
  SourceCardId, SourceInstanceId,
  RootSourceCardId, RootOwnerSide,
  TargetInstanceId,
  Amount, Lethal, CauseEventId
}
```

死亡事件必须引用致死原因。首次击杀奖励按 `RootOwnerSide` 过滤，而非按死亡方猜测。

### 6.5 复仇

不足：若每个技能自行计数，衍生物死亡、同时死亡和重生边界容易不一致。

改进：由战斗方状态维护统一 `AvengeTracker`，只消费合法友方死亡事件；每个监听器声明阈值、余数保留规则和触发次数。触发生成的新死亡在同一事件队列继续处理。

### 6.6 目标与模式快照

不足：使用棋盘索引会因克隆、排序或对手阵容变化指向错误对象；使用招募阶段实例 ID 也可能无法映射到战斗克隆；目标丢失后自动选第一个通常不是真实规则。

改进：招募阶段保存 `HeroPowerSelectionState`；开战时解析成不可变 `CombatSelectionSnapshot`：

```csharp
CombatSelectionSnapshot {
  PowerCardId,
  OwnerSide,
  SelectionKind,        // FriendlyInstance / EnemySlot / Mode / None
  RecruitInstanceId,
  CombatInstanceId,
  SlotAtLock,
  ChoiceId,
  ValidityPolicy,       // Cancel / KeepSlot / DeterministicFallback
  Consumed
}
```

目标失效策略必须逐技能配置并测试，禁止公共逻辑默认“取第一个”。

### 6.7 战斗临时与永久状态

不足：直接在战斗克隆上加永久属性不会自动回写；直接改招募棋盘又会污染战斗快照。死亡之翼的“永久”尤其需要明确哪些实体可回写。

改进：战斗中的变更统一标注 `CombatOnly`、`PersistentToRecruit` 或 `RewardOnly`。永久回写必须通过原始实体映射和独立 ledger，只回写合法的招募阶段实体；临时生成物不能凭实例名误回写。

### 6.8 上一场战斗历史

不足：只保存“最后一个死亡友方随从”无法支持发现池、首次击杀、双方阵容猜测等需求；保存已附魔实例又会错误生成非白板复制。

改进：保存规范化 `CombatHistoryRecord`，包括双方开战阵容、所有死亡事件、基础 CardId、是否金色、来源和胜负。白板奖励只用 CardId 从 catalog 重建，并移除金色、附魔、临时关键词和战斗伤害。

## 7. 目标架构

### 7.1 唯一契约

```csharp
interface ICombatHeroPowerHandler
{
    string PowerCardId { get; }
    void BuildSnapshot(CombatSnapshotBuilder builder, HeroPowerRuntimeState state);
    void Register(CombatHeroPowerRegistry registry, CombatHeroPowerSnapshot snapshot);
}
```

`CombatHeroPowerSnapshot` 至少包含：

- `PowerCardId`、英雄 CardId、所有者方；
- 是否激活、使用次数、一次性技能是否已消费；
- 选择目标/模式快照；
- 本场计算所需计数器的只读副本；
- 可写回状态的显式白名单；
- 数据版本和技能实现版本。

### 7.2 双边对称

玩家与敌方必须通过同一个 builder：

```text
MatchState.Player  ─┐
                    ├─ CombatSnapshotBuilder ─ CombatContext
OpponentState      ─┘
```

禁止长期保留“玩家 HeroEffectEngine + 敌方专用 switch”两套实现。编辑器配置敌方技能时，也应生成相同结构的 `HeroPowerRuntimeState`。

### 7.3 统一事件循环

推荐阶段：

1. `SnapshotLocked`：锁定双方棋盘、手牌、英雄技能选择和计数；
2. `CombatCreated`：创建 replay 初始帧；
3. `StartOfCombatQueued`：双方所有开战动作进入排序队列；
4. `StartOfCombatResolving`：逐动作执行，每个动作产生结构化事件；
5. `ImmediateAttacksResolving`：清空立即攻击队列；
6. `NaturalCombat`：自然攻击循环；
7. 每个原子动作后统一执行伤害、死亡、亡语、复仇、召唤、空位监听和新立即攻击；
8. `CombatFinalized`：确定胜负和伤害；
9. `WritebackBuilt`：只生成回写命令；
10. `WritebackApplied`：MatchService 原子应用奖励、永久增益和历史。

### 7.4 开战顺序策略

当前实现用随机种子确定双方部分开战准备顺序，但英雄技能又在该顺序之外提前执行。迁移后必须把顺序显式化：

- 所有同时声明“开战时”的动作进入同一排序域；
- 先按目标酒馆版本规定的阶段分组，再按先手方/稳定序号执行；
- 尚无公开可核验规则的同阶段细节，应标记为 `RuleUncertain`，以真实客户端录制用例校准；
- 不得用 C# 方法调用顺序充当未记录的游戏规则。

## 9. 实施计划

### P0：先修共享基础设施

1. 新建双边 `CombatHeroPowerSnapshot`，从玩家和敌方同一路径构建；
2. 新建结构化 `CombatEvent` 与来源链，覆盖伤害、攻击、击杀、死亡、召唤、空位变化、立即攻击；
3. 新建统一 `SummonResolver`、`AvengeTracker`、`ImmediateAttackQueue`；
4. 把英雄开战效果纳入 CombatEngine 的统一队列和 replay；
5. 新建 writeback ledger，禁止战斗逻辑直接随意修改长期 MatchState；
6. 首批迁移伊利丹、塔维什、布鲁坎、奥妮克希亚、泰隆、奥苏玛特、范达尔/德雷克塔尔、格雷布、拉法姆、死亡之翼。

完成标准：上述英雄玩家侧与敌方侧使用相同 handler；删除或停止调用对应的敌方专用分支；全流程测试能证明结果而非只证明标志。

### P1：迁移复杂快照和历史能力

- 奥拉基尔、塔姆辛、亚煞极、恩佐斯、希尔瓦娜斯、瓦托格尔；
- 完成亡语描述快照、白板复制工厂、完整 CombatHistoryRecord；
- 为规则不确定处补真实客户端对照夹具。

### P2：主动技能与 UI

- 统一友方实例、敌方槽位、模式选择 UI；
- UI 显示“已锁定目标/模式”“目标失效后的规则”“本场是否已消费”；
- 泽瑞克等一次性技能使用后，模型和 UI 同步锁定。

### P3：移除代理和重复路径

- 移除已经迁移的 `ApplyCombatStartEffects` 英雄专用分支；
- 移除 `ApplyOpponentCombatStartHeroPowers` 对应重复 switch；
- 战后 proxy 只保留真正的 `RewardOnly` 能力；
- 对遗留字段增加过期注释和迁移断言，随后删除。

### P4：版本化与全量审计自动化

- 从英雄数据自动生成“需要的事件能力”清单；
- CI 检查每个战斗相关 HeroPower CardId 是否注册 handler、双边测试和持久化策略；
- 数据版本变化时输出新增、文本变化、类别变化和失去实现映射的英雄。

## 10. 测试矩阵

### 10.1 每个英雄必须具备的四层测试

| 层级 | 必须断言 | 不足以单独通过的证据 |
|---|---|---|
| Handler 单元测试 | 输入快照生成正确动作/监听器 | CardId 命中某个 `if` |
| CombatEngine 集成测试 | 棋盘、事件序列、攻击者、死亡链、胜负 | 仅 Tavern 标志或日志字符串 |
| MatchService 端到端 | 选择 -> 快照 -> 战斗 -> 回写 -> 清理 | 直接调用 helper |
| 双边黑盒测试 | 玩家/敌方交换后规则对称，随机种子可复现 | 只测玩家侧 |

### 10.2 必测边界

- 空棋盘、满棋盘、开战时满但死亡后出现空位；
- 单随从时最左与最右是同一实例；
- 最高/最低属性并列；
- 目标在开战前被替换、移除或变形；
- 双方都有开战技能和立即攻击；
- 技能伤害同时杀死多个随从；
- 圣盾吸收、免疫、0 攻、重生、亡语召唤、召唤失败；
- 复仇一次跨越多个阈值；
- 拉法姆面对自毁、环境伤害、敌方自杀和英雄技能致死；
- 永久增益的原始随从死亡、存活、变形和生成物；
- 同一种子重复模拟事件序列完全相同；
- 玩家/敌方互换后，除先手规则外结果镜像一致。

### 10.3 代表性验收用例

1. **伊利丹单随从**：同一随从只获得一次规定增益，立即攻击次数符合真实规则；
2. **泰隆满场**：目标开战死亡后进入待复活状态；无空位不强行插入，出现空位后立即合法复活完全复制；
3. **奥苏玛特满场转空位**：开战时不召唤，首次出现空位时触发；
4. **拉法姆归属**：敌方先因自身效果死亡不计，首个由玩家根来源造成的击杀才生成奖励；
5. **奥妮克希亚复仇**：同时死亡按统一死亡队列累计，雏龙召唤后立即攻击并正确衔接后续自然攻击；
6. **死亡之翼双边**：双方合法原始实体获得永久增益；临时召唤物不写回招募阵容；
7. **亚煞极**：战斗召唤对象与战后获得对象来源一致，手牌满时使用统一奖励溢出规则；
8. **希尔瓦娜斯**：候选来自上一场完整死亡集合，返回白板非金色基础复制。

## 11. 验收标准

只有同时满足以下条件，某个战斗英雄技能才可标记为“完成”：

- 数据中的当前 CardId 和文本版本已锁定；
- 玩家与敌方使用同一 handler；
- 目标/模式能从 UI 或测试配置稳定进入战斗快照；
- 技能在正确事件阶段执行并出现在结构化 replay 中；
- 能正确影响本场棋盘、攻击、死亡链和胜负，或生成准确的 RewardOnly 回写；
- 临时与永久状态边界通过测试；
- 至少包含正常、空/满场、目标失效、双方同时存在和固定种子回归用例；
- 不依赖日志字符串作为唯一断言；
- 对尚不确定的真实顺序有明确标记和对照用例，不伪装成已确认规则。

全局完成还要求：数据扫描出的全部战斗相关英雄均进入覆盖矩阵，不允许依靠人工逐个搜索 CardId。

## 12. 自动审计方案：避免以后逐个手查

新增编辑器/测试脚本，读取 `battlegroundsHeroes.json`，按以下特征自动识别候选：

- `primaryCategory == Combat`；
- 文本包含 Start of Combat、in combat、after combat、last combat、attack、kill、die、damage、summon、Avenge；
- handler 元数据声明需要 Combat 事件。

为每个候选输出：

```text
CardId | 英雄 | 数据版本 | 能力分类 | Handler | 双边支持
目标模型 | 所需事件 | 持久化策略 | 单元测试 | 集成测试 | 黑盒测试 | 状态
```

CI 失败条件：

- 新增候选但没有 handler 或显式 `NotApplicable` 说明；
- handler 只支持一方；
- 声明 `Persistent` 却没有 writeback 测试；
- 声明 `Kill/Death/Summon/Avenge` 却没有对应事件测试；
- CardId 文本变化但实现版本和基线未更新。

该自动审计机制也适用于金色随从、饰品和伙伴：核心不是人工枚举，而是“数据候选 -> 能力声明 -> handler -> 测试证据”的闭环。

## 13. 风险、回滚与不确定性

### 13.1 风险

- 调整开战顺序会改变大量固定种子结果；
- 统一死亡队列可能暴露现有亡语、复仇、重生测试中的近似行为；
- 永久回写错误会污染招募阵容，是最高数据风险；
- 删除敌方专用路径前若覆盖不足，会造成敌方能力回退。

### 13.2 控制措施

- 每批只迁移一组共享机制，保留旧路径 feature flag；
- 新旧引擎在固定场景下双跑，比较结构化事件而非只比较最终胜负；
- writeback 先以只读预览 ledger 运行，确认后再启用写入；
- 只有某 CardId 的双边矩阵全部通过后，才删除旧分支。

### 13.3 尚需真实客户端校准

- 多个不同来源“开战时”效果的精确相对顺序；
- 双方同时立即攻击时的完整优先级；
- 部分“有空位时”能力在一条死亡链中的触发窗口；
- 补丁版本变化后的数值、解锁回合和轮换可用性。

这些项目应标记为待校准，不应以当前方法调用顺序推断官方规则。

## 14. 实施完成定义

本方案完成后的系统应满足：新增一个战斗英雄技能时，开发者只需声明技能 CardId、事件订阅、目标模型和持久化策略；玩家与敌方自动获得同一行为，replay 自动记录，审计工具自动要求相应测试。任何技能都不能只因为写了标志、打印了日志或战后补了一张牌而被误判为“已经实现”。
