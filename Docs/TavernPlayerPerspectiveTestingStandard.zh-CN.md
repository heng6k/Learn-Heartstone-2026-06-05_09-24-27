# 酒馆模拟器玩家视角测试与实现真实性规范

## 1. 文档目的

本文定义酒馆模拟器的统一测试方法，重点解决以下问题：

- 白盒测试通过，但功能只存在于字段、注册表或内部方法中。
- 按钮对象存在，但玩家看不到、点不到或无法理解。
- 直接调用命令可以成功，但真实点击、拖拽、弹窗和 Raycast 流程失败。
- Editor 中可以运行，但实际构建缺少图片、字体、Prefab、JSON 或本地化资源。
- 领域状态发生变化，但卡牌、日志、回放和提示没有向玩家表达。
- 测试把 `ConfiguredOnly`、`DisplayOnly` 或 `Partial` 误标为 `Implemented`。

本文适用于：

- 新功能开发。
- 卡牌、英雄、任务、饰品、畸变和时空酒馆机制接入。
- UI 重构和视觉优化。
- Bug 修复和回归测试。
- Alpha/正式构建发布验收。

## 2. 核心原则

### 2.1 白盒通过不等于玩家功能存在

白盒测试证明的是：特定输入下某段代码返回了预期结果。

它不能单独证明：

- 玩家能够找到功能入口。
- 控件在当前分辨率下可见。
- 鼠标可以命中控件。
- 透明 Image 没有阻挡 Raycast。
- 拖拽能够经过真实 EventSystem 到达合法目标。
- 描述和提示足以让玩家理解结果。
- 状态变化真正显示在卡面、日志和回放中。
- 资源进入了实际 Player Build。

因此：

> 白盒测试证明“代码路径可能工作”；玩家旅程和实际 Build 验收才证明“功能对玩家真实存在”。

### 2.2 测试结果必须以玩家可观察事实为主

优先验证：

- 屏幕显示的名称、描述、图标和状态。
- 金币、酒馆等级、生命、商店、手牌和战场变化。
- 按钮是否可见、可点、可理解。
- 弹窗是否正确打开、关闭和返回。
- 关键词是否获得、保持和消失。
- 战斗帧和回放是否解释真实结算。
- 失败操作是否说明原因并保持状态不变。

内部字段、方法调用次数和事件计数可以作为诊断证据，但不能替代玩家结果。

### 2.3 测试名称必须说明证据等级

测试不能用模糊名称让人误以为已经完成玩家验收。

推荐命名：

```text
WhiteBox_TimewarpedPurchase_DeductsConfiguredCostOnce
ViewIntegration_DisabledUpgrade_ShowsInsufficientGoldReason
PlayMode_DragShopCardToHand_BuysThroughEventSystem
PlayerJourney_FromLaunchToCombatReplay_CompletesWithoutInternalCalls
BuildAcceptance_ZhCnCardLibrary_RendersLocalizedDescriptions
```

不推荐：

```text
TimewarpWorks
UiIsCorrect
FeatureImplemented
FullAcceptance
```

## 3. 标准测试分层

## 3.1 L0：静态数据和注册完整性

### 目的

验证数据、资源和注册关系是否存在。

### 可以验证

- CardId 是否进入卡牌目录。
- 图片路径是否存在。
- 中文名称和描述是否存在。
- Effect/Handler 是否完成注册。
- Prefab 引用是否配置。
- 卡牌是否被标记为正确的实现状态。

### 不能证明

- 效果实际正确运行。
- 玩家能够在卡库中找到它。
- UI 能够显示图片和描述。
- 实际构建包含资源。

### 典型输出

- 数据覆盖报告。
- 图片覆盖报告。
- 本地化覆盖报告。
- 实现状态注册表检查。

## 3.2 L1：白盒领域和应用规则测试

### 目的

验证领域规则、命令边界和纯计算。

### 允许使用

- 直接调用 Engine、Service、Command Handler。
- 构造领域模型。
- 修改测试专用状态。
- Mock/Fake 数据仓库。
- 检查事件计数和内部状态。

### 必须覆盖

- 正常成功路径。
- 资源不足、满手牌、满战场、无目标等失败路径。
- 临时/永久效果到期。
- 重复命令和幂等。
- 普通版和金色版。
- 酒馆阶段和战斗阶段边界。
- 保存/加载或状态复制时需要保持的字段。

### 限制

L1 通过后，功能最多可以标记为 `LogicVerified`，不能直接标记为玩家可用。

## 3.3 L2：View 和组件集成测试

### 目的

验证领域状态能够正确转换成 UI 组件状态。

### 最低检查项

- 对象存在且 `activeInHierarchy == true`。
- `CanvasGroup.alpha`、`interactable`、`blocksRaycasts` 正确。
- RectTransform 与屏幕有有效交集。
- 关键文本非空且符合当前语言。
- Button、ScrollRect、InputField 和拖拽组件配置正确。
- 禁用按钮显示原因。
- 弹窗遮罩层和关闭按钮顺序正确。
- 卡面、详情、日志和回放展示同一权威状态。

### 关于 `FindChild`

`FindChild` 只能证明对象被创建，不能证明玩家能使用。

下面的测试不构成玩家验收：

```csharp
Assert.IsNotNull(FindChild(root, "UnityTimewarpedTavernButton"));
```

至少还要验证：

```text
对象处于激活状态
位于屏幕范围内
没有被更高层 Overlay 遮挡
Raycast 可以命中
按钮可交互或显示明确禁用原因
文本和图标正确
操作后产生玩家可观察结果
```

## 3.4 L3：Unity PlayMode 真实输入测试

### 目的

验证真实 Unity 输入链，而不是直接调用监听器。

### 必须通过的路径

- PointerDown → PointerUp → Click。
- BeginDrag → Drag → EndDrag → Drop。
- ScrollRect 滚动。
- 输入框搜索和筛选。
- 打开/关闭弹窗。
- Escape 或界面取消按钮。
- 重复快速点击。

### 禁止替代真实输入的做法

以下调用可以用于 L1/L2，但不得作为 L3/L4 的被测动作：

```csharp
button.onClick.Invoke();
service.Apply(command);
controller.BeginDrag(...);
controller.HandleDrop(...);
service.State.Player.Tavern.Gold = 100;
```

### 场景夹具例外

为了避免每个测试都从第一回合慢慢搭建复杂局面，可以使用测试场景夹具快速准备前置状态。

但必须满足：

- 夹具只负责准备前置局面。
- 被测动作必须通过玩家入口完成。
- 测试报告明确哪些步骤由夹具完成。
- 夹具不能直接写入被测试的最终结果。

例如可以通过夹具准备一个拥有圣盾来源法术的手牌，但“打出法术并选择目标”必须走真实 UI 输入。

## 3.5 L4：玩家黑盒旅程测试

### 目的

从玩家可访问入口完成跨页面、跨系统流程。

### 玩家旅程测试约束

- 从主大厅或明确场景入口开始。
- 不读取或修改内部领域状态。
- 不直接调用私有方法、Controller 命令和按钮监听器。
- 只使用玩家能看到的按钮、卡牌、输入框、滚动区域和拖拽目标。
- 断言以玩家可观察结果为主。
- 允许在失败后读取日志进行诊断，但日志不能替代界面反馈。

### 旅程测试通过条件

- 玩家能发现下一步操作。
- 操作可以真实完成。
- 成功结果清晰可见。
- 失败原因清晰可见。
- 返回和取消不会丢失上下文。
- 不需要知道内部 CardId、命令名或对象名。

## 3.6 L5：实际 Player Build 验收

### 目的

验证 Editor 外的真实发布环境。

### 必须检查

- Windows Player 可以正常启动和退出。
- Resources、Prefab、字体、图片、JSON 和本地化资源已打包。
- 不依赖 `UNITY_EDITOR` 分支才能加载主要资源。
- 不出现粉色材质、Missing Sprite、默认字体替换和空卡图。
- Player.log 无业务异常。
- 分辨率、窗口缩放和 DPI 不造成关键阻断。
- 保存路径、文件权限和中文路径正常。

### 结论

只有 L5 通过，功能才可以获得 `BuildVerified` 证据。

## 4. 证据等级和实现状态

## 4.1 证据等级

| 等级 | 名称 | 说明 |
| --- | --- | --- |
| E0 | DataPresent | 数据、字段或资源存在 |
| E1 | LogicVerified | 白盒规则测试通过 |
| E2 | ViewVerified | UI 正确展示当前状态 |
| E3 | InteractionVerified | 真实 PlayMode 输入可以完成操作 |
| E4 | JourneyVerified | 玩家完整旅程通过 |
| E5 | BuildVerified | 实际 Player Build 验收通过 |

证据必须逐级累积。E1 不能自动推导 E2–E5。

## 4.2 功能实现状态

| 状态 | 定义 | 最低证据 |
| --- | --- | --- |
| Missing | 没有数据或没有入口 | 无 |
| DataOnly | 只有数据、图片或描述 | E0 |
| DisplayOnly | UI 可以展示，但没有真实效果 | E0 + 部分 E2 |
| ConfiguredOnly | 可以配置，但不会完整影响对局 | E0 + E2 |
| FrameworkFirst | 公共架构存在，具体效果不完整 | E1 |
| Partial | 部分条件、目标或边界已实现 | E1 + 部分 E2/E3 |
| LogicComplete | 规则层完成，但尚未玩家验收 | E1 |
| PlayerUsable | 玩家可以真实使用 | E1–E4 |
| Implemented | 规则、UI、旅程和构建全部通过 | E1–E5 |
| OutOfScope | 明确不属于当前项目范围 | 范围文档依据 |

### 硬性规则

- 只有 E1 不得标记为 `Implemented`。
- 只有按钮、配置页面或描述不得标记为 `Implemented`。
- 实际行为与描述不一致时，状态最高为 `Partial`。
- Editor 通过但 Build 未验证时，状态最高为 `PlayerUsable`。
- 任何 `Implemented` 条目都必须能够追溯到对应的旅程和 Build 验收结果。

## 5. “假通过”禁止规则

## 5.1 不以对象存在证明功能完成

错误示例：

```csharp
Assert.IsNotNull(FindChild(root, "UnityCardLibraryOverlay"));
```

这个断言无法发现：

- Overlay 在屏幕外。
- 尺寸为零。
- 被其他遮罩覆盖。
- 没有可关闭路径。
- 列表无法滚动。
- 内容全部未翻译。

## 5.2 不以监听器调用证明按钮可用

错误示例：

```csharp
button.onClick.Invoke();
Assert.AreEqual(expectedGold, service.State.Player.Tavern.Gold);
```

这绕过了：

- Button 是否可见。
- Button 是否被遮挡。
- EventSystem 是否存在。
- GraphicRaycaster 是否工作。
- 指针位置是否能命中。
- 重复点击是否被锁定。

## 5.3 不以字段变化证明玩家理解了变化

错误示例：

```csharp
Assert.IsTrue(minion.Keywords.Contains(Keyword.DivineShield));
```

还必须验证：

- 卡面显示圣盾状态。
- 详情显示统一中文说明。
- 获得时有短期反馈。
- 消耗时有消失反馈。
- 回放对应帧显示正确。

## 5.4 不以无异常证明行为正确

测试仅断言“不抛异常”不能证明：

- 命令产生正确效果。
- 失败时没有部分写入状态。
- 资源没有被重复扣除。
- UI 没有进入无法返回状态。

每个测试必须同时检查预期变化和不应变化的字段。

## 5.5 不以测试专用数据掩盖真实资源问题

如果测试总是注入完整 Sprite、字体和本地化文本，就无法发现实际 Resources 缺失。

至少一组 Build 验收必须使用正式资源加载路径。

## 6. 玩家角色定义

## 6.1 主要测试角色：熟悉酒馆玩法的普通玩家

这个角色：

- 理解购买、刷新、冻结、升本、摆位和战斗。
- 不知道项目内部命令、CardId、Handler 和调试字段。
- 第一次使用本模拟器时不会阅读代码和开发文档。
- 希望快速构造局面并理解战斗结果。

测试人员应持续问：

- 我现在知道下一步点哪里吗？
- 这个按钮为什么不可用？
- 操作是否真的成功？
- 局面变化来自哪张卡？
- 为什么这次触发了或没有触发？
- 我能否返回上一层而不丢失配置？

## 6.2 辅助测试角色

### 第一次接触模拟器的玩家

重点检查入口、快速开始、术语解释和错误恢复。

### 高级构筑测试玩家

重点检查卡库筛选、自由选择、对手配置、复杂场景和回放解释。

### 小窗口玩家

重点检查 1280×720、1000×600 和 994×384 下的布局、滚动和文字。

## 7. 标准玩家旅程

## 7.1 PJ-01：启动和进入酒馆

### 步骤

1. 启动实际 Player Build。
2. 查看主大厅。
3. 进入酒馆训练器。
4. 使用快速开始或自定义对局。
5. 选择英雄、种族、卡池和高级机制。
6. 进入酒馆桌面。

### 玩家可观察结果

- 主大厅只有一个明确的酒馆入口。
- 不可用模块不会抢占主视觉。
- 中文模式没有中英文混用。
- 每个选择项有足够描述。
- 高级机制与基础设置分层。
- 返回时不会无提示丢失修改。

### 失败信号

- 两个同名入口。
- 出现 `Close`、`Done`、内部枚举或 CardId。
- 按钮超出屏幕或无法滚动到。
- 玩家不知道必须选择多少种族。

## 7.2 PJ-02：基础招募操作

### 步骤

1. 查看金币、酒馆等级和商店。
2. 刷新。
3. 冻结和解冻。
4. 购买一张随从。
5. 从手牌拖到战场。
6. 调整站位。
7. 出售随从。
8. 升级酒馆。

### 玩家可观察结果

- 操作前能够判断费用和可用性。
- 操作后金币、商店、手牌和战场立即一致。
- 拖拽目标有清晰提示。
- 资源不足时说明具体原因。
- 重复快速点击不会重复扣费。

## 7.3 PJ-03：定向英雄技能和法术

### 步骤

1. 点击一个需要目标的英雄技能或法术。
2. 查看来源和合法目标。
3. 点击非法目标。
4. 取消定向。
5. 再次进入定向并选择合法目标。

### 玩家可观察结果

- 清楚显示“正在为哪个效果选择目标”。
- 合法与非法目标不只通过颜色区分。
- 显示取消方式。
- 非法选择不消耗资源。
- 成功后目标状态和反馈一致。

## 7.4 PJ-04：时空酒馆完整流程

### 步骤

1. 配置饰品和同回合时空酒馆触发。
2. 推进回合。
3. 完成饰品选择。
4. 进入时空酒馆。
5. 浏览和查看商品描述。
6. 测试资源不足、满手牌和正常购买。
7. 快速连续点击购买。
8. 退出时空酒馆。
9. 检查普通商店。
10. 推进战斗和下一回合。

### 玩家可观察结果

- 饰品先、时空酒馆后。
- 时空酒馆不会重复打开。
- 失败购买不扣资源、不移除商品。
- 正常购买只发生一次。
- 普通商店没有被错误刷新或覆盖。
- 未完成时空酒馆前不能越过强制流程。
- 退出后普通酒馆恢复正确。

## 7.5 PJ-05：关键词获得、保持和消失

### 步骤

1. 选择一个当前没有圣盾的随从。
2. 通过真实 UI 让它获得圣盾。
3. 查看卡面和详情。
4. 开始战斗并让圣盾被消耗。
5. 查看战斗回放。

### 玩家可观察结果

- 获得时显示“获得圣盾”或等价反馈。
- 卡面持续显示圣盾状态。
- 详情中显示统一中文说明。
- 消耗时显示破裂/失去反馈。
- 后续帧不再显示圣盾。
- 回放和日志标明变化来源。

相同旅程应扩展到嘲讽、复生、风怒、潜行和烈毒/剧毒。

## 7.6 PJ-06：对手配置和工具

### 步骤

1. 打开对手面板。
2. 添加对手随从。
3. 配置对手英雄技能、任务奖励和饰品。
4. 修改一个对手随从属性。
5. 关闭工具并返回主桌面。

### 玩家可观察结果

- 正常玩法和调试工具视觉分层。
- 每个配置项有中文描述。
- 卡库可搜索、过滤和滚动。
- 返回后保留主桌面上下文。
- 对手状态在战斗和回放中生效。

## 7.7 PJ-07：战斗和回放解释

### 步骤

1. 配置双方战场。
2. 开始完整下一回合。
3. 播放、暂停、切换速度。
4. 查看上一帧和下一帧。
5. 查看攻击、圣盾、死亡、亡语和复生。
6. 返回酒馆。

### 玩家必须能够回答

- 为什么由这个随从攻击？
- 为什么选择了这个目标？
- 哪个效果改变了身材或关键词？
- 圣盾、烈毒或复生在何时消耗？
- 为什么召唤失败或溢出？
- 战斗为什么结束或达到安全步数限制？

## 7.8 PJ-08：错误恢复和返回

覆盖：

- 空卡库。
- 搜索无结果。
- 资源不足。
- 满手牌和满战场。
- 不存在合法目标。
- 未完成强制选择时推进回合。
- 退出酒馆确认。
- 弹窗多层打开和返回。

要求失败操作：

- 提示原因。
- 不产生部分状态变化。
- 不让界面卡死。
- 保留用户已完成的有效配置。

## 8.2 时空酒馆

| 场景 | 必须断言 |
| --- | --- |
| 同回合饰品和时空酒馆 | 顺序正确，不覆盖选择 |
| 重复进入 | 只生成一次状态和商品 |
| 重复购买 | 只扣费、发牌和触发一次 |
| 购买失败 | 状态原子性，禁止触发计数为 0 |
| 退出 | 普通商店快照正确恢复 |
| 保存加载/UI 重建 | 商品、资源、状态不丢失 |
| 未完成流程推进回合 | 被阻止并给出玩家提示 |

## 8.3 UI 和交互

| 项目 | 检查方法 |
| --- | --- |
| 可见性 | 屏幕交集、CanvasGroup、层级和截图 |
| 可点击性 | GraphicRaycaster + PointerEventData |
| 遮挡 | 检查最上层命中对象是否为预期控件 |
| 拖拽 | 真实 EventSystem 完整事件链 |
| 滚动 | 实际滚动到首尾并选择内容 |
| 弹窗 | 打开、覆盖、返回、关闭和焦点恢复 |
| 响应式 | 五种关键分辨率截图和 RectTransform 审计 |
| 禁用状态 | 原因文本、视觉区别和不可执行 |

## 8.4 关键词

每个核心关键词至少覆盖：

- 初始不存在。
- 真实操作获得。
- 卡面持续保持。
- 详情说明。
- 战斗中生效。
- 消耗、到期或移除。
- 回放跳帧一致性。
- UI 重建后不重复播放获得动画。

## 9. 视觉验收

自动化对象断言不能完全替代视觉检查。

### 必须截图的状态

- 主大厅。
- 基础设置和高级设置。
- 满商店、满战场、满手牌。
- 打开 Inspector、工具和卡库。
- 时空酒馆。
- 关键词获得和消失。
- 7 对 7 战斗回放。
- 错误 Toast 和确认弹窗。

### 截图检查项

- 重叠和越界。
- 字体、乱码和截断。
- 可操作与不可操作状态。
- 主次信息层级。
- 遮罩透明度和弹窗顺序。
- 关键词是否遮挡名称、攻血和卡图。
- 当前语言是否一致。

### 截图差异的使用边界

- 视觉快照可以发现布局回归。
- 不能只依赖像素完全一致，因为动画、字体渲染和平台差异可能产生噪声。
- 应同时使用布局指标、对象状态和人工视觉抽查。

## 10. 日志、异常和性能检查

## 10.1 日志要求

每个玩家旅程结束后检查：

- Unity Console。
- Player.log。
- 项目业务错误和异常堆栈。
- Missing Reference、Missing Sprite、字体 fallback 和资源加载失败。

不允许以 Toast 显示错误后仍继续产生异常作为“已处理”。

## 10.2 性能观察

UI 和回放旅程至少观察：

- 点击普通操作是否造成整棵 UI 重建。
- Layout rebuild 峰值。
- GC Alloc。
- 打开大卡库时的卡顿。
- 连续回放时对象创建和销毁。
- 关键词短期动画是否重复实例化大量对象。

性能不是所有功能测试的阻塞项，但明显卡顿、输入丢失和长时间无响应属于玩家功能失败。

## 11. 自动化与人工测试分工

## 11.1 适合自动化

- 领域计算和边界。
- 实现状态、翻译和资源覆盖。
- UI 对象状态和布局指标。
- 真实指针点击和标准拖拽。
- 固定玩家旅程。
- 时空酒馆禁止触发计数。
- 关键词帧状态一致性。
- Build 启动冒烟和日志扫描。

## 11.2 必须保留人工体验测试

- 玩家是否容易发现入口。
- 描述是否真正易懂。
- 信息层级是否合理。
- 卡面是否过于拥挤。
- 关键词动画是否清晰但不打扰。
- 回放是否足以解释战斗。
- 长时间使用工具和卡库是否疲劳或混乱。

人工测试必须记录具体场景和结论，不能只写“感觉不错”。

## 12. 测试用例标准格式

每个玩家视角用例使用以下格式：

```markdown
## 用例编号和名称

### 玩家目标

### 前置条件
- 使用哪个正式场景或测试夹具。
- 当前语言、分辨率和构建版本。

### 玩家操作
1. 只描述玩家可以执行的动作。
2. 不写内部命令和状态修改。

### 预期可观察结果
- 玩家看到什么。
- 哪些资源和区域发生变化。
- 哪些内容必须保持不变。

### 失败信号
- 哪些表现代表功能未实现或发生回归。

### 自动化证据
- 测试名称。
- 截图路径。
- 日志和结果文件。

### 实现真实性结论
- E0–E5 证据等级。
- Missing/DataOnly/Partial/PlayerUsable/Implemented。
```

## 14. 实现真实性矩阵

每个卡牌、英雄技能或机制建议维护以下列：

| 字段 | 说明 |

| Id/名称 | 稳定标识和本地化名称 |
| 数据导入 | 是否存在正式数据 |

| 中文描述 | 是否完整且与实现一致 |

| L4 玩家旅程 | 测试结果链接 |

| 最终状态 | Missing/Partial/PlayerUsable/Implemented |

## 15. 测试报告必须区分的结论

测试报告禁止只写：

```text
全部测试通过，功能已完成。
```

必须分别报告：

```text
白盒规则测试：通过/失败/未运行
View 集成测试：通过/失败/未运行
真实输入测试：通过/失败/未运行
玩家旅程：通过/失败/未运行
实际 Build：通过/失败/未运行
人工体验：通过/有条件通过/失败/未检查
```

如果只有白盒通过，应写：

```text
规则层已验证；玩家可用性和实际构建尚未验证，不能标记为 Implemented。
```

## 16. 发布门槛

## 16.1 每次合并前

- 相关 L0/L1 测试通过。
- 至少一个 L2 View 测试证明状态可见。
- 影响交互时必须增加 L3 真实输入测试。
- 更新实现真实性状态，不允许无证据升级为 `Implemented`。

## 16.2 每个阶段完成前

- 对应玩家旅程通过。
- 关键分辨率布局通过。
- Console 无新增业务异常。
- 文档中的验收标准逐条记录结果。

## 16.3 每次发布前

- L1 白盒规则测试全绿。
- 核心 L3 真实输入测试全绿。
- PJ-01 至 PJ-08 核心旅程通过。
- 实际 Windows Player Build 验收通过。
- 本地化覆盖缺失为 0。
- 时空酒馆禁止触发计数为 0。
- 关键词状态、日志和回放一致。
- 五种关键分辨率无 P0/P1 布局问题。
- Player.log 无业务异常。
