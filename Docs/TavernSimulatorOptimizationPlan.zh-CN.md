# 酒馆模拟器当前优化与改进详细计划

## 1. 目标

本计划作为当前酒馆模拟器优化工作的统一执行入口，合并以下来源：

- 用户新增的翻译、时空酒馆、UI 排版、美化和关键词状态反馈要求。
- 2026-07-11 全流程审核发现的问题。
- 现有 UI、时空酒馆和高级机制专题文档中仍有效的建议。

最终目标不是简单“让界面更漂亮”，而是同时达到：规则正确、信息完整、交互清楚、视觉统一、便于继续维护。

## 2. 本轮范围

### 纳入本轮

1. 所有卡牌库和选择界面的中文描述与本地化覆盖。
2. 时空酒馆开启、购买、退出和高级机制顺序的触发安全。
3. 主大厅、设置流程、酒馆桌面、弹窗、工具和回放的排版优化。
4. UI Design Tokens、组件状态和酒馆风格视觉美化。
5. 随从关键词获得、保持、消失的对外显示。
6. 重复入口、Modal Stack、禁用原因、定向取消、快速开始和局部刷新。

### 本轮暂缓

- 完整手柄导航、方向导航图和手柄 glyph。
- 大规模重写领域层或替换全部 UGUI 技术栈。
- 与当前五项要求无关的卡牌效果补齐。

## 3. 完成定义

只有同时满足以下条件，本轮才能标记完成：

- 全局要求文档中的相关验收项全部通过。
- 卡牌库和选择界面本地化缺失为 0。
- 时空酒馆禁止触发测试全部通过。
- 关键分辨率无阻断级重叠、越界和不可访问控件。
- 主大厅只有一个明确的酒馆训练器入口。
- 关键词获得、保持和消失都有实际视觉反馈及自动化验证。
- 现有酒馆核心测试无回归，Console 无项目业务错误。

## 4. 优先级总览

| 优先级 | 工作包 | 原因 |
| --- | --- | --- |
| P0 | 时空酒馆触发安全和状态保护 | 可能产生重复结算、扣费和状态污染，必须先保证规则正确 |
| P1 | 全卡库/选择界面翻译完整性 | 直接影响用户理解规则和选择结果 |
| P1 | 主入口、Modal Stack、禁用原因和定向取消 | 影响完整操作路径和误操作率 |
| P1 | UI 信息架构与响应式排版 | 当前主要可用性问题 |
| P2 | 关键词获得/保持/消失反馈 | 提高规则可见性和回放解释能力 |
| P2 | 视觉系统和美化 | 在布局稳定后统一完成，避免反复返工 |
| P2 | UI 局部刷新和组件边界 | 降低焦点丢失、滚动复位和维护成本 |
| Deferred | 手柄导航 | 用户明确要求暂不实施 |

## 5. Phase 0：基线、术语和测试入口

### 目标

先建立后续修改都能复用的检查基线，避免改完只靠截图判断。

### 工作内容

- 建立统一术语表：卡牌类型、种族、关键词、任务、奖励、饰品、畸变、时空酒馆状态。
- 建立玩家可见文本清单，区分：名称、描述、提示、按钮、错误、空态、日志和调试字段。
- 建立当前关键页面截图基线：
  - 主大厅。
  - 种族/英雄/卡池设置。
  - 高级机制设置。
  - 酒馆桌面。
  - 对手配置。
  - 工具和各类卡库。
  - 战斗回放。
- 固定测试分辨率：1920×1080、1366×768、1280×720、1000×600、994×384。
- 建立交互检查表：打开、关闭、确认、取消、禁用、重复点击、滚动、空数据和错误恢复。

### 建议测试

- `TavernLocalizationCoverageTests`
- `TavernCriticalLayoutAcceptanceTests`
- `TavernModalRouteAcceptanceTests`

### 验收标准

- 后续每个 Phase 都能引用相同的术语和页面清单。
- 测试能够输出缺少翻译、控件越界和关键按钮尺寸不足的具体对象名。

## 6. Phase 1：时空酒馆触发安全

### 目标

让时空酒馆成为独立、可恢复、不可重复触发的状态流程。

### 设计建议

#### 6.1 明确状态机

建议至少区分：

1. `Closed`：未开启。
2. `Scheduled`：本回合应开启，但被更高优先级选择阻塞。
3. `Open`：正在浏览和购买。
4. `ResolvingPurchase`：处理单次购买，防止重复提交。
5. `Completed`：本次时空酒馆完成，等待回到普通酒馆。

不要用多个无约束布尔值表达这些互斥状态。

#### 6.2 高级机制队列

- 饰品选择优先于时空酒馆。
- 不再依赖单个 `PendingChoice` 覆盖后写入的机制。
- 使用明确队列、优先级或“当前选择 + 待恢复选择”结构。
- 每个待处理项带稳定 Id，重复恢复不会生成第二份。

#### 6.3 命令幂等和输入锁

- 进入、购买、退出命令在处理期间禁用对应按钮。
- 同一购买命令重复提交只成功一次。
- 失败时不扣资源、不移除商品、不推进状态。
- UI Rebuild 不得重新调用进入或生成商品逻辑。

#### 6.4 事件隔离

建立允许触发白名单，不依赖“先执行普通购买再撤销副作用”。

重点检查：

- 普通刷新事件。
- 普通购买事件。
- 任务、饰品和英雄计数。
- 三连。
- 回合开始/结束。
- 战斗开始。
- 普通商店冻结和槽位。

### 建议修改区域

- `TavernMatchModels.cs`：时空酒馆状态和高级机制队列。
- `MatchService.cs`：回合顺序、进入/购买/退出和幂等保护。
- `GameCommand.cs`：明确的时空酒馆命令和稳定请求 Id。
- `UnityTavernTrainerController.cs`：按钮锁定、状态显示和错误反馈。

### 测试矩阵

| 场景 | 预期 |
| --- | --- |
| 同回合同时满足饰品和时空酒馆 | 先完成饰品，再恢复同一份时空酒馆 |
| 连续点击进入 | 只生成一次商品和一次状态变更 |
| 连续点击购买 | 只扣费和发牌一次 |
| 满手牌购买 | 明确失败，商品和资源不变 |
| 资源不足购买 | 明确失败，不触发购买相关计数 |
| 打开时推进回合/战斗 | 被阻止并说明需先完成时空酒馆 |
| 退出后普通商店 | 商品、冻结和槽位状态正确恢复 |
| UI 重建/保存加载 | 时空酒馆状态和商品保持一致 |

### 验收标准

- 禁止触发计数全部为 0。
- 无重复扣费、重复发牌、重复任务进度和重复高级机制选择。
- 任意失败路径都保持领域状态原子性。

## 7. Phase 2：描述翻译和卡库/选择器统一

### 目标

玩家在任何卡牌库和选择流程中，都能用当前语言完整理解候选项。

### 设计建议

#### 7.1 统一本地化入口

- 建立单一 `LocalizedCardPresentation` 或等价服务。
- UI 不直接拼接原始 JSON 字段、枚举 `ToString()` 或内部 Notes。
- 统一返回：名称、描述、类型标签、关键词、实现状态和缺失原因。

#### 7.2 描述规范化

- 清理 `[x]`、富文本残留和不支持标签。
- 统一数字和关键词强调。
- 保留“临时”“永久”“本回合”“战斗中”“酒馆中”等限制词。
- 对模拟器尚未完全实现的效果增加明确状态标签，不能伪装成完整实现。

#### 7.3 覆盖所有入口

必须逐一检查：

- 卡池编辑器中的随从、法术和时空酒馆标签页。
- 工具中的玩家手牌、对手手牌、对手战场、敌方战斗法术卡库。
- 英雄、英雄技能、伙伴卡库。
- 任务、奖励、小饰品、大饰品、畸变和自由选择。
- 发现和第二英雄技能选择。
- 卡牌详情、悬停关键词说明、战斗回放和日志。

#### 7.4 列表信息层级

- 卡片表面显示名称、关键数值、类型和短描述。
- 完整描述进入详情区或可展开区域。
- 长列表使用统一搜索、过滤、空态和结果数。
- 禁用候选显示具体原因。

### 测试矩阵

- 每个选择器至少构造一个中文、英文、长描述、缺描述和未实现候选。
- 中文/英文切换后验证当前已打开列表和详情。
- 检查玩家可见字符串是否含裸枚举名或内部占位符。
- 生成全量覆盖报告，按 CardKind 和高级机制类型分类。

### 验收标准

- 玩家可见翻译缺失为 0。
- 不再出现 `Close`、`Done`、`Reward` 等无意的中英文混用。
- 任何选择前都能看到足以判断结果的描述。

## 8. Phase 3：入口和设置流程收敛

### 目标

减少进入酒馆前的困惑，让新用户快速开始、高级用户仍能完整配置。

### 工作内容

- 删除主大厅第二个同名“酒馆训练器”镜像入口。
- 隐藏或弱化 4 个未开放模块，不再与主入口同级。
- 主入口提供：
  - `快速开始`：推荐默认种族、英雄和卡池。
  - `自定义对局`：进入完整配置。
  - `最近配置`：可选，恢复上次设置。
- 第一页只选择英雄、种族和卡池版本。
- 高级机制放到下一页：任务/奖励、饰品、畸变、时空酒馆。
- 卡池编辑器增加独立的时空酒馆筛选/编辑入口，与随从和法术一致。
- 离开存在未保存修改的编辑器前进行确认。

### 验收标准

- 主大厅不存在同名同功能的重复按钮或重复 GameObject 名。
- 新用户最多两次主要点击即可用默认配置进入酒馆。
- 高级设置不会干扰只想开始普通对局的用户。
- 任务与任务奖励在配置界面明确成对显示。

## 9. Phase 4：酒馆桌面排版和交互优化

### 目标

让用户在进入桌面后的 3 秒内找到局面和主要操作。

### 信息架构

#### 常驻主层

- 回合、金币、生命、酒馆等级。
- 商店、己方战场、手牌。
- 英雄技能、刷新、冻结、升级、完整下一回合。

#### 按需展开层

- 卡牌详情和可执行操作。
- 对手详情和机制配置。
- 建议、日志和回放时间线。

#### 工具层

- 发牌、编辑属性、替换高级机制、覆盖报告等调试功能。
- 使用明显的工具/调试视觉标识，不和正常玩法按钮混在同一层级。

### 重点改动

- 右侧面板统一为可折叠 Inspector Drawer。
- 工具、卡库、详情、回放和确认弹窗使用统一 Modal Stack。
- 禁用按钮可悬停并显示具体原因。
- 定向技能/法术显示来源、合法目标和“Esc/右键取消”提示。
- Toast 使用队列，不因下一次无关刷新立即消失。
- 保存弹窗打开前的焦点、选中卡、标签页和滚动位置。
- 卡牌上的操作按钮减少，主要动作移到选中区或稳定操作栏。

### 响应式规则

- Wide：可常驻 Inspector。
- Standard：Inspector 默认折叠。
- Compact：隐藏辅助区、压缩区域间距、保留最小字号和按钮高度，必要时滚动。
- 不通过把所有字号缩小到 10–12 来适配小窗口。

### 验收标准

- 必测分辨率没有关键越界和不可滚动弹窗。
- 主要按钮目标高度至少 44，辅助按钮不得低于可可靠点击范围。
- 禁用、选择、危险和工具状态无需阅读说明也能初步区分。
- 打开和关闭弹窗后，用户仍回到原来的上下文。

## 10. Phase 5：UI 美化和 Design Tokens

### 目标

在布局稳定后统一视觉语言，形成可持续迭代的酒馆风格。

### Design Tokens

至少统一：

- 背景、一级表面、二级表面、浮层和遮罩颜色。
- 主操作、经济、战斗、危险、收益、工具、选中和禁用语义色。
- 标题、区域标题、正文、辅助文字和徽标字号。
- xs/sm/md/lg 间距。
- 卡牌、按钮、chip、弹窗和 Inspector 尺寸。
- normal/hover/pressed/selected/disabled 的边框、阴影和亮度。

### 视觉方向

- 桌面和卡牌保留暖色酒馆质感。
- 信息面板使用更中性的深色表面，避免所有区域都呈现相同棕绿。
- 金色主要用于资源、奖励和关键确认，不滥用于所有标题。
- 战斗、错误和危险使用红色并配合图标/文字。
- 调试工具使用独立蓝紫或冷色标识。
- 装饰图像默认关闭 raycast。

### 动画规范

- 普通按钮反馈：100–150ms。
- 弹窗淡入/轻微缩放：150–220ms。
- Toast：快速出现，按内容长度停留，淡出后进入历史记录。
- 支持减少动态效果时，保留文字和状态变化。

### 验收标准

- 同类控件视觉一致，不再由每个组件自行定义颜色和尺寸。
- 不看文字也能区分主操作、危险、工具和禁用状态。
- 美术装饰不会遮挡卡牌数值、名称和交互目标。

## 11. Phase 6：随从关键词状态反馈

### 目标

让玩家明确看到关键词何时获得、当前是否保持、何时消失以及变化来源。

### 数据和事件设计

增加可供 UI 消费的关键词变化记录，建议字段包括：

- 目标 `InstanceId`。
- `Keyword`。
- 变化类型：`Gained`、`Refreshed`、`Lost`、`Consumed`。
- 来源 CardId/InstanceId。
- 持续范围：永久、当前酒馆阶段、当前战斗、直到触发。
- 发生阶段和回放帧 Id。

UI 以当前权威状态决定“保持”，以事件决定“刚刚获得/消失”的短期动画。

### 视觉层级

#### 获得

- 卡牌上方显示“获得圣盾”等短文字。
- 对应关键词图标弹入并短暂发光。
- 回放事件链显示来源→目标→关键词。

#### 保持

- 核心关键词使用稳定图标、外框或卡牌标记。
- 最多在卡面显示 2–3 个最高优先级关键词，完整列表放入详情。
- 临时关键词使用小时钟、虚线边框或“临时”角标。

#### 消失

- 圣盾破裂、复生消耗、烈毒消耗等使用具有语义的短动画。
- 其他关键词使用淡出或划除，并显示“失去/消耗”文字。
- 动画结束后图标必须与真实状态一致。

### 首批关键词

- 嘲讽。
- 圣盾。
- 剧毒/烈毒。
- 复生。
- 风怒。
- 潜行。
- 亡语、战吼等触发型关键词先保证稳定徽标和详情说明，动态触发效果可分批完善。

### 测试矩阵

- 酒馆阶段获得永久关键词。
- 酒馆阶段获得临时关键词并在到期时消失。
- 战斗中圣盾被消耗。
- 烈毒/剧毒消耗或状态移除。
- 复生触发后标记消失，新实例状态正确。
- UI 重建后不重复播放获得动画。
- 回放跳帧时直接恢复该帧状态，不错误重播所有历史动画。

### 验收标准

- 玩家无需打开日志也能知道随从当前拥有的核心关键词。
- 每次获得和消失至少有文字或图标变化，不只依赖颜色。
- UI、日志和回放对同一次变化使用相同术语和来源。

## 12. Phase 7：Modal Stack、局部刷新和组件边界

### 目标

解决整棵 UI 重建带来的焦点、滚动、Toast 和维护问题。

### 工作内容

- 建立 `TavernModalCoordinator`：统一打开、覆盖、返回和关闭。
- 普通状态变化改为局部刷新：
  - 资源 → TopBar。
  - 商店 → Shop Zone。
  - 战场/手牌 → 对应 Zone。
  - 选中卡 → Inspector。
  - 关键词事件 → 对应 Card View 和通知层。
- 保存 ScrollRect 位置和当前筛选条件。
- Toast 独立于主内容重建。
- 将主控制器逐步拆分为 TopBar、Board、Shop、Hand、Inspector、Modal 等 presenter/component。

### 注意事项

- 不进行一次性大重写。
- 每拆一个区域先补测试，再替换旧刷新路径。
- 保留 Prefab 缺失时的开发期 fallback，但必须输出明确 warning。

### 验收标准

- 点击普通按钮不再销毁整个训练器 UI 树。
- 打开卡库并选择/过滤后，返回时保持原滚动和筛选上下文。
- Toast 和关键词短期反馈不被无关局部刷新清除。

## 13. 推荐实施顺序

1. Phase 0：基线、术语和测试入口。
2. Phase 1：时空酒馆触发安全。
3. Phase 2：描述翻译和选择器统一。
4. Phase 3：入口和设置流程收敛。
5. Phase 4：酒馆桌面排版和交互优化。
6. Phase 5：视觉系统和美化。
7. Phase 6：关键词状态反馈。
8. Phase 7：Modal Stack、局部刷新和组件拆分。

时空酒馆正确性和翻译完整性必须先于大规模视觉改造，否则 UI 美化会掩盖规则错误并造成重复返工。

## 14. 每阶段交付格式

每个 Phase 完成时应同时交付：

- 改动文件清单。
- 新增/更新测试及结果。
- 关键分辨率截图。
- 未完成和 Deferred 项。
- 已知风险。
- 对全局要求文档中相关验收项的逐条结果。
- 按 [TavernPlayerPerspectiveTestingStandard.zh-CN.md](TavernPlayerPerspectiveTestingStandard.zh-CN.md) 分别报告白盒、View、真实输入、玩家旅程和 Build 证据。

## 15. 本轮不做但必须保留兼容性

完整手柄导航暂缓。当前 UI 优化仍应：

- 使用标准 Unity `Selectable` 控件。
- 不用只支持鼠标悬停的唯一交互。
- 保持稳定的控件对象名和逻辑顺序。
- 弹窗保留明确的确认与取消操作。

这些只用于避免未来接入成本，本轮不要求编写方向导航、手柄提示或平台 glyph。
