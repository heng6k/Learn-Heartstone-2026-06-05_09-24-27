# 敌我双方全局成长参数一致性审计

## 1. 审计结论

训练工具中的十项“敌我双方全局参数”目前并不是一套完全对称的系统。

界面将它们统一表现为双方都可增减的数值，但底层实际分为四类：

1. 双方确实有战斗消费者，但只支持少数指定效果，例如法强。
2. 玩家功能完整，敌方只有字段和临时状态，没有通用效果入口，例如酒馆法术身材加成。
3. 双方能够生效，但必须先发生特定触发，例如鲜血宝石品质。
4. 玩家会随正常流程自动成长，敌方只能手动配置，不会从战斗结果持续成长。

因此，之前的测试通过并不代表十项参数已经实现敌我完整对称。多数测试验证的是：

- 命令能否写入字段。
- 敌我字段是否互不污染。
- 参数能否复制到临时战斗状态。
- 个别指定卡牌能否读取该参数。

它们没有完整验证：

> 工具修改 → 已有卡牌更新 → 进入战斗 → 实际触发 → 战斗后持久成长 → 保存/加载后仍一致。

## 2. Root Cause Analysis

**现象**：工具中的数值已经调整，部分卡牌或战斗效果却没有按显示值变化；同一个参数通过不同入口设置时结果不同；玩家与敌方成长速度或卡面数值不一致。

**预期**：同名参数在玩家和敌方拥有清晰一致的语义；如果某项只支持特定效果，UI 应明确说明；字段测试通过时应有对应的最终行为测试。

**根因**：

1. 玩家和敌方使用不同的权威状态及生命周期。
2. “参数已保存”与“存在效果消费者”被混为一谈。
3. 已有卡牌是否重算依赖具体操作入口和操作顺序。
4. 战斗奖励只持久化玩家侧，敌方不会自动成长。
5. 场景系统重复保存同一组玩家参数，并存在静默覆盖。
6. 部分测试只覆盖字段或直接构造 CombatEngine 状态，未覆盖工具到最终效果的完整链路。

**建议修复方向**：统一参数权威状态；为每项参数声明明确适用范围；集中处理已有卡牌重算；决定敌方是否需要自动成长；删除场景中的重复数据源；将测试升级为逐参数、逐侧、逐入口的端到端矩阵。

**预防**：以后新增全局参数时必须同时登记“状态源、消费者、是否回溯已有牌、是否自动成长、敌方支持级别、端到端测试”。

## 3. 当前状态结构并不对称

参数类型定义在 `SideCombatModifierKind`，共十项，参见 `TavernMatchModels.cs:1010`。

### 玩家

玩家同时保存两份数据：

- `State.Player.CombatModifiers`
- `State.Player.Tavern` 中的对应字段

工具修改玩家参数时，先写 `CombatModifiers`，再整组复制进 `TavernState`，参见 `MatchService.cs:18143`。

每条游戏命令完成后，又会从 `TavernState` 回写 `CombatModifiers`，参见 `MatchService.cs:1848` 和 `MatchService.cs:18189`。

实际权威状态因此更接近 `Player.Tavern`。

### 敌方

敌方只将 `Opponent.CombatModifiers` 作为持久配置。进入战斗时才新建一个临时 `TavernState`，把十项参数复制进去，参见 `MatchService.cs:18226`。

这只能证明“数值进入了战斗状态”，不能证明战斗内存在读取它的卡牌或效果。

## 5. 已确认的具体缺陷

### 5.1 玩家已有永恒骑士和星元自动机不会随工具值重算

玩家工具修改参数后只执行 `ApplyPlayerCombatModifiersToTavern`，不会调用：

- `ApplyEternalKnightBonuses`
- `ApplyAncestralAutomatonBonuses`

玩家战斗开始时 `CreateCombatStartPlayerBoard` 也只是克隆现有卡牌，不进行补算。

所以可能出现：

- 工具显示“永恒死 5”。
- TavernState 中也是 5。
- 已经在战场上的永恒骑士仍带旧附魔。
- 战斗中继续使用旧身材。

现有 UI 只对玩家亡灵攻击提示“手动修改不会重算已有永久牌”，但永恒骑士和星元自动机同样受影响。

### 5.2 复制或镜像玩家战场后，敌方参数可能不生效

添加或编辑敌方卡牌时，会调用 `ApplyOpponentCombatModifiersToRetainedCards`，参见 `MatchService.cs:18536`。

但“复制玩家战场到敌方”和“镜像玩家战场”只克隆卡牌，不调用敌方成长重算，参见 `MatchService.cs:20096`。

克隆还会保留玩家侧已有附魔。如果卡牌上已经存在以下来源：

- `Undead Attack Bonus`
- `Eternal Knight`
- `Ancestral Automaton`

敌方战斗开始逻辑会认为该成长已经应用，从而跳过敌方参数补算，参见 `CombatEngine.cs:774`。

因此操作顺序会影响结果：

- 先复制，再修改敌方参数：通常会触发重算。
- 先修改敌方参数，再复制：复制出的牌可能继续携带玩家旧成长。

### 5.3 内置 SpellFlow 场景会静默丢失玩家酒馆法术 +3/+2

`TestScenarioMapper.ApplyTo` 先从 `ScenarioTavernState` 写入玩家成长，随后又调用 `ApplyPlayerModifiersToTavern`，用 `PlayerCombatModifiers` 覆盖同一组字段，参见 `TestScenarioMapper.cs:103`、`TestScenarioMapper.cs:129` 和 `TestScenarioMapper.cs:179`。

内置 SpellFlow 场景将玩家酒馆法术加成写为：

- `scenario.Tavern.TavernSpellBonusAttack = 3`
- `scenario.Tavern.TavernSpellBonusHealth = 2`

但没有同步设置 `scenario.PlayerCombatModifiers`，其默认值为 0/0。加载后 +3/+2 会被静默覆盖为 0/0。

现有 `DesignValidationToolingTests` 没有检查 SpellFlow 加载后的实际数值，因此测试仍然通过。

### 5.4 敌方不会从战斗奖励自动成长

战斗结束后只执行：

```text
ApplyCombatRewards(result.PlayerRewards)
```

参见 `MatchService.cs:21648`。

没有对 `result.OpponentRewards` 做对应持久化。`ApplyCombatRewards` 内部也全部写向 `State.Player.Tavern`，参见 `MatchService.cs:22117`。

因此敌方以下数据不会随战斗自然增加：

- 永恒骑士死亡数。
- 友方随从死亡数。
- 其他依赖 CombatReward 的全局成长。

敌方工具区当前更接近“静态场景参数编辑器”，不是完整的敌方成长系统。

### 5.5 敌方酒馆法术身材加成基本没有通用消费者

`TavernSpellEngine` 的身材加成读取硬编码为 `state.Player.Tavern`，例如 `TavernSpellEngine.cs:509` 和 `TavernSpellEngine.cs:1004` 附近。

敌方虽然拥有 `TavernSpellBonusAttack/Health` 字段，但没有一条通用的“敌方招募阶段施放酒馆法术”路径。

将该参数复制进敌方临时 TavernState 并不会自动给敌方随从加身材。

### 5.6 敌方鲜血宝石品质只有条件性效果

鲜血宝石品质不是光环。只有某个具体效果调用 `CombatEngine.ApplyBloodGem` 时才读取对应数值。

例如特定饰品在战斗中打宝石时可以读取敌方临时 TavernState；普通敌方随从、已有卡面和未触发宝石效果的战斗不会发生变化。

覆盖报告将鲜血宝石品质标记为 `TestCovered=true`，参见 `MechanicCoverageReportService.cs:15`，但现有与 `SideCombatModifierKind.BloodGem*` 直接相关的测试主要验证字段写入和场景往返，缺少工具命令到敌方实际增强宝石的端到端测试。

## 6. 为什么测试通过但仍会对不上

### 6.1 字段测试不等于效果测试

`Apply_SideCombatModifiersAreIndependent` 只证明：

- 玩家宝石攻击能设为 3。
- 敌方宝石攻击能设为 1。
- 两边字段不会互相覆盖。

它没有让敌方实际打出一颗鲜血宝石并检查身材。

### 6.2 直接 CombatEngine 测试绕过了工具和状态同步

法强测试直接构造带 `SpellPower` 的 TavernState 并调用 CombatEngine。

这证明 `GetCombatSpellDamage` 正确，参见 `CombatEngine.cs:8298`，但没有验证：

> 工具按钮 → GameCommand → Opponent.CombatModifiers → CreateOpponentCombatTavernState → 指定英雄技能 → 战斗伤害。

### 6.3 场景往返测试的数据本来就是一致的

`TestScenarioMapperTests` 从玩家 TavernState 捕获场景。捕获时会自动生成一致的 PlayerCombatModifiers，再加载回来。

它没有构造“ScenarioTavernState 为 +3/+2，而 PlayerCombatModifiers 为 0/0”的冲突数据，所以无法发现覆盖顺序问题。

### 6.4 覆盖报告是静态声明

`MechanicCoverageReportService` 返回手写布尔值，不会扫描实际消费者或测试。

`CombatResultExplainer` 也只是看到配置值大于零就生成变量信号，参见 `CombatResultExplainer.cs:70`。它不能证明该参数在本场战斗中实际被消费。

## 7. Unity MCP 验证

本次未修改运行时代码，仅通过 Unity MCP 端口 6400 运行现有相关测试：

| 测试 | 结果 | 说明 |
|---|---:|---|
| `OpponentCustomizationTests` | 14/14 通过 | 覆盖敌方三类历史成长、字段独立性、塔维什/布鲁坎法强样例；未覆盖其他参数完整链路 |
| `TestScenarioMapperTests` | 2/2 通过 | 覆盖一致数据的保存/加载往返；未覆盖双来源冲突 |
| `DesignValidationToolingTests` | 6/6 通过 | 覆盖场景目录、亡灵场景与解释器信号；未检查 SpellFlow 加载后的 +3/+2 |

这些结果与根因并不冲突：测试覆盖的切片能够通过，但切片之间的连接和对称性存在缺口。

## 8. 建议修复优先级

### P0：消除确定性错误

1. 解决场景中 `ScenarioTavernState` 与 `PlayerCombatModifiers` 的重复权威问题。
2. 复制/镜像玩家战场后统一重算敌方历史成长，并移除或替换玩家侧追踪附魔。
3. 玩家工具修改永恒骑士/星元自动机参数后重算已有战场、手牌和商店卡牌。

### P1：明确敌方成长模型

需要明确二选一：

- 敌方参数只是静态战斗场景输入。
- 敌方拥有完整的自动成长和战斗奖励持久化。

如果选择静态输入，UI 应改名为“敌方场景参数”，并标明不会自动增长。

### P1：收紧参数语义

- “法术”改为“本局酒馆法术数”。
- “法强”注明“仅支持已接入的战斗法术伤害”。
- “酒法攻/血”在敌方侧标为未接入，或在实现前禁用。
- “宝石攻/血”注明“只影响之后实际打出的鲜血宝石”。
- “复仇死”改为“本局友方死亡数”，并注明敌方当前无通用消费者。

### P2：升级测试矩阵

每个参数至少增加以下测试：

1. 玩家工具命令写入。
2. 敌方工具命令写入。
3. 已有战场卡牌是否按设计回溯。
4. 新加入战场/手牌卡牌是否按设计计算。
5. 复制/镜像入口。
6. 保存/加载入口。
7. 实际效果消费者。
8. 战斗后是否自动成长或保持静态。

## 9. 最终判断

目前问题不是某一个公式算错，而是“统一 UI 下隐藏了多套不同生命周期”。

最需要优先处理的是：

1. 场景加载的双状态覆盖。
2. 玩家已有历史牌不重算。
3. 复制/镜像敌方战场继承玩家旧附魔。
4. 敌方参数不会从战斗奖励自动成长。
5. 酒馆法术、鲜血宝石、友方死亡数等参数只有部分或条件性消费者，却以完整对称能力展示。

在这些问题解决前，工具中的数字更适合作为“配置值”，不能全部视为最终卡面或战斗结果的可靠预测。

## 10. 修复落地结果（2026-07-11）

本轮已经完成以下修复：

1. 场景模型增加玩家参数权威来源标记。新建和重新保存的场景以 `PlayerCombatModifiers` 为唯一参数快照；旧场景继续以 `ScenarioTavernState` 中的重叠字段为准，避免旧数据静默丢失。
2. 内置 SpellFlow 场景的酒馆法术 +3/+2 已同时登记到权威参数快照，加载后不再被 0/0 覆盖。
3. 玩家和敌方共用同一套已有卡牌回算入口。工具修改亡灵攻击、永恒骑士死亡数和星元自动机召唤数后，会立即更新战场、手牌以及玩家商店中的相关卡牌。
4. 加载场景、重置战斗快照、复制玩家战场和镜像玩家战场后都会执行统一回算；玩家侧旧附魔会被移除或替换为敌方配置值。
5. 战斗结束后，敌方会持久化状态模型能够表达的奖励：永恒骑士死亡、友方随从死亡、鲜血宝石品质、酒馆法术身材品质和亡灵攻击成长。
6. 工具标签改为明确语义，例如“本局酒馆法术数”“战斗法强”“宝石攻（打出时）”“本局友方死亡”，不再将条件性参数表现成通用光环。
7. 战斗解释器与覆盖报告改为区分“已经配置”与“本场实际存在消费者”。

仍然保留的设计边界：敌方没有完整的招募阶段与通用酒馆法术施放系统，因此敌方酒馆法术身材加成只会在已接入的具体效果或战斗奖励路径中使用；本轮没有虚构第二套敌方招募玩法。

专项与相邻 Unity MCP 6400 测试共 213 项通过。完整工具视图组另有两个与本修复无调用关系的既有问题：商店随从测试数据偶发为空，以及高级种族池编辑器用例超过 180 秒；本轮聚焦的全局参数工具视图用例单独运行通过。
