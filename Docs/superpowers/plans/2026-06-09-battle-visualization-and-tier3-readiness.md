# 战斗可视化与三本扩展前置项目文档

> 给后续执行的 Agent：本阶段不要急着铺三本卡牌。先把战斗过程和对手战场编辑做成可观察、可回放、可复现的调试工具，再进入三本机制池扩展。目标是让每一张新牌都有固定场景、固定 seed、可视化回放和白盒日志支撑。

## 一、阶段结论

当前项目的一本、二本已经进入“可跑基础战斗闭环”的状态：

- 已有保存场景、加载场景、固定 seed、一键战斗测试、战斗后重置到战前快照等基础链路。
- 已补齐一批关键底层差距：攻击指针轮转、召唤位置、风怒、立即攻击、部分亡语、进击、战后奖励、全局记录、塑造法术临时清理。
- EditMode 测试已经能覆盖一批一二本核心机制，说明当前架构可以继续扩展。

但站在酒馆战棋玩家和卡牌游戏开发主管角度，现在还不适合直接大规模加入三本：

- 三本开始机制密度明显提高，亡语、复仇、进击、战斗中召唤、持续光环、塑造法术、永久成长会互相影响。
- 当前战斗过程仍主要依赖日志和测试断言，站位变化、攻击顺序、召唤插入位置、临时 buff 清理不够直观。
- 对手战场虽然能自定义，但缺少足够舒服的可视化操作，不利于快速构造复杂复现场景。

因此下一阶段明确优先级为：

1. 战斗可视化回放调试器 v1。
2. 对手战场可视化编辑器 v1。
3. 基于可视化调试能力，再按机制池推进三本随从和法术。

## 二、阶段目标

本阶段目标不是做正式对局动画，而是做开发调试用的“战斗显微镜”：

- 能从当前玩家战场和对手战场直接开始战斗。
- 能记录每一步战斗状态快照。
- 能上一帧、下一帧、跳到事件。
- 能在 UI 上高亮攻击者、目标、死亡随从、召唤物、触发来源。
- 能点击日志事件后定位到对应战斗帧。
- 能更舒服地编辑对手战场：拖拽排序、修改身材和关键词、复制玩家战场、一键清空、一键保存测试场景。

做完后，后续补三本时每个机制都应能做到：

- 有固定测试场景。
- 有固定随机种子。
- 有黑盒结果断言。
- 有白盒事件日志断言。
- 能通过战斗回放肉眼确认攻击顺序、站位和触发时机。

## 三、范围边界

本阶段覆盖：

- 单人酒馆战棋战斗调试。
- 玩家战场与自定义对手战场。
- 一本、二本现有机制的可视化验证。
- 为三本机制扩展预留事件和 UI 框架。

本阶段不做：

- 双打机制，包括队友、传递、双打专属文本和收益。
- 正式产品级战斗动画和特效。
- 完整 Hearthstone 事件栈重写。
- 三本卡牌的大规模实装。
- 网络 API 自动同步卡库。

注意：酒馆法术和普通法术必须继续区分。酒馆刷新中出现的是“酒馆法术”；鲜血宝石、黏黏盾、尖利箭矢、塑造法术等按普通法术或特殊衍生法术处理，不应占用酒馆随从刷新格。

## 四、战斗回放调试器 v1

### 4.1 数据结构目标

新增或扩展战斗回放模型，建议包含以下概念：

- `CombatReplay`
  - `Seed`
  - `InitialSnapshot`
  - `Frames`
  - `Result`
  - `Rewards`
- `CombatFrame`
  - `Index`
  - `EventType`
  - `ActorSide`
  - `ActorId`
  - `TargetSide`
  - `TargetId`
  - `PlayerBoardSnapshot`
  - `OpponentBoardSnapshot`
  - `LogText`
  - `RelatedEntityIds`
- `CombatBoardSnapshot`
  - 当前随从顺序。
  - 攻击力、生命值、最大生命值。
  - 圣盾、嘲讽、风怒、复生、烈毒、剧毒等关键词。
  - 本场战斗临时标签，例如是否来自亡语召唤、是否被光环影响、是否已攻击。
- `CombatEventType`
  - `CombatStarted`
  - `AttackDeclared`
  - `DamageResolved`
  - `DivineShieldBroken`
  - `VenomousResolved`
  - `DeathQueued`
  - `DeathrattleResolved`
  - `MinionSummoned`
  - `RebornResolved`
  - `RallyResolved`
  - `AvengeProgressed`
  - `SpellcraftTemporaryApplied`
  - `CombatEnded`

首版不需要一步到位做完整事件栈，但每个 frame 必须能说明“这一帧发生了什么”和“哪些实体受影响”。

### 4.2 战斗引擎要求

战斗引擎需要支持两种输出：

- 现有的最终战斗结果，用于游戏逻辑继续运行。
- 新增的完整回放数据，用于 UI 和测试验证。

实现建议：

- 不要把 UI 逻辑写进 `CombatEngine`。
- 在领域层生成纯数据回放。
- UI 层只消费 `CombatReplay`。
- 当前日志可以继续保留，但应尽量从结构化事件派生显示文本。
- 每次关键状态变化后都记录 snapshot，而不是只记录文字日志。

必须优先覆盖的帧：

- 战斗开始双方初始场面。
- 每次攻击前：标出攻击者和目标。
- 每次伤害后：显示双方身材变化。
- 圣盾破裂、烈毒/剧毒结算、死亡入队。
- 亡语结算和 token 召唤位置。
- 复生结算和复生位置。
- 立即攻击，例如暮光龙崽。
- 风怒第二次攻击。
- 战斗结束和战后奖励。

### 4.3 UI 要求

战斗测试区域右侧或弹层中加入回放调试器。首版 UI 以清晰和可查错为目标，不追求炫酷动画。

需要包含：

- 顶部：当前回放名、seed、帧编号、结果。
- 中间：玩家战场和对手战场的战斗快照。
- 底部：上一帧、下一帧、播放/暂停、回到开始、跳到结束。
- 右侧：结构化事件日志列表。
- 点击日志：跳到对应帧，并高亮相关随从。
- 高亮状态：
  - 攻击者。
  - 目标。
  - 本帧受伤随从。
  - 本帧死亡随从。
  - 本帧召唤随从。
  - 本帧触发来源。

移动和小窗口要求：

- 整个页面必须支持滚轮滚动。
- 顶部 UI 不允许因为购买牌或面板变多被压缩到看不清文字。
- 关键操作按钮固定可见或在滚动后仍容易找到。

## 五、对手战场可视化编辑器 v1

当前对手战场自定义已经能满足基础调试，但三本以后需要更快构造局面。下一版对手战场编辑器要做到“鼠标点几下就能复现复杂战斗”。

### 5.1 必做功能

- 拖拽排序：对手随从可拖动改变站位。
- 点选编辑：点击随从后在编辑面板修改攻击、生命、关键词、金色状态、种族。
- 一键清空：清空对手战场。
- 一键复制：复制当前玩家战场到对手战场。
- 一键镜像：按相反顺序复制玩家战场，用于测试左右站位差异。
- 一键保存场景：把玩家战场、手牌、酒馆、对手战场、回合、金币、等级、seed 保存为测试场景。
- 一键加载场景：从保存列表恢复。

### 5.2 关键词编辑

关键词编辑应使用清晰的开关控件：

- 嘲讽。
- 圣盾。
- 风怒。
- 复生。
- 烈毒。
- 剧毒。
- 潜行，如后续加入。

不要把关键词写成需要手输的自由文本。调试器的目标是降低复现场景成本。

### 5.3 卡牌来源

对手战场添加卡牌时优先使用当前卡池数据：

- 支持按名称搜索。
- 支持按等级筛选。
- 支持按种族筛选。
- 支持按机制标签筛选，例如亡语、战吼、进击、复仇、塑造法术、光环、召唤。

后续如果接官方数据，应优先参考：

- [Blizzard Hearthstone Game Data API](https://develop.battle.net/documentation/hearthstone/game-data-apis)
- 本地文档：[Docs/OFFICIAL_APIS.md](../../OFFICIAL_APIS.md)

## 六、测试计划

### 6.1 白盒测试

为 `CombatReplay` 增加 EditMode 测试：

- 攻击事件会生成 `AttackDeclared` 帧。
- 伤害后 snapshot 中身材正确变化。
- 圣盾破裂会生成对应事件。
- 亡语召唤位置在死亡随从附近。
- 复生位置正确。
- 风怒会生成两次攻击事件。
- 立即攻击会生成插入式攻击事件。
- 哼鸣蜂鸟后续召唤野兽能在 snapshot 中体现攻击加成。
- 血色骷髅 buff 目标不依赖死亡结算遍历顺序。
- 战斗结束 frame 包含胜负和奖励。

### 6.2 黑盒测试

使用保存场景验证最终结果：

- 一本基础野兽召唤局。
- 二本森林游虫甲虫加成局。
- 二本亮喉督军召唤并给 token 鲜血宝石局。
- 暮光龙崽亡语召唤雏龙并立即攻击局。
- 爆裂飓风风怒攻击局。
- 泰蕾苟萨永久保留战斗 buff 局。
- 塑造法术直到下回合临时清理局。

### 6.3 UI 验收

- 开始战斗后能看到双方战前快照。
- 点击下一帧能逐步查看攻击、伤害、死亡、亡语、召唤、结束。
- 点击日志能跳转并高亮相关随从。
- 页面滚动正常，顶部信息不被压缩。
- 对手战场可拖拽排序。
- 对手随从可点选修改身材和关键词。
- 保存场景后重新加载，战斗回放结果在同 seed 下保持一致。

## 七、验收标准

本阶段完成需要同时满足：

- Unity EditMode 测试全绿。
- 至少新增 8 个战斗回放相关测试。
- 至少新增 3 个对手战场编辑相关测试或可验证用例。
- 一本、二本代表场景可以通过 UI 回放确认。
- 回放数据不依赖 Unity UI 对象，领域层可单独测试。
- 没有引入双打机制。
- 酒馆法术和普通法术仍在数据和刷新逻辑中明确区分。

## 八、三本扩展启动顺序

完成战斗可视化后，再进入三本。三本不要按卡牌列表硬铺，应按机制池推进。

### 8.1 第一组：亡语与召唤

目标：验证死亡、召唤、召唤位置、召唤后光环、亡语顺序。

实施方式：

- 先选三本中最代表性的亡语/召唤牌。
- 每张牌建立固定测试场景。
- 每张牌必须有回放帧证明召唤位置和触发顺序。

### 8.2 第二组：复仇、受伤、攻击触发

目标：验证事件计数、受伤时机、攻击后触发和死亡后的计数归属。

实施方式：

- 先补通用事件计数器。
- 再接具体随从效果。
- 回放日志里必须能看到计数变化。

### 8.3 第三组：战斗开始与持续光环

目标：验证开战快照、后续召唤是否吃光环、光环来源死亡后是否仍持续。

实施方式：

- 将“本场战斗持续效果”做成明确的 combat modifier。
- snapshot 中标记随从当前受到哪些来源影响。

### 8.4 第四组：塑造法术与战后收益

目标：验证“直到下回合”“永久保留”“战后给手牌/酒馆/玩家状态”的边界。

实施方式：

- 继续区分酒馆法术、普通法术、塑造法术、衍生特殊法术。
- 完善临时效果清理事件。
- 回放和招募阶段日志都要能看到收益来源。

## 九、执行顺序

建议按以下顺序开发：

1. 增加 `CombatReplay` / `CombatFrame` 纯数据模型。
2. 让 `CombatEngine` 在现有结果之外输出结构化 replay。
3. 给现有一二本测试补 replay 断言。
4. 做战斗回放 UI：帧切换、日志点击、高亮。
5. 做对手战场拖拽排序和点选编辑。
6. 做保存/加载场景与 replay 的联动。
7. 用一二本代表场景做完整白盒/黑盒验证。
8. 验证完成后再开三本机制池。

## 十、风险与注意事项

- 不要为了 UI 回放改坏战斗规则。规则层只产出数据，显示层只消费数据。
- 不要把战斗 replay 做成字符串日志集合；后续三本需要结构化事件。
- 不要忽略召唤位置。三本以后相邻、攻击指针、复仇和亡语都会被它影响。
- 不要把三本机制直接塞成特判。优先补机制池，再挂具体卡牌。
- 不要引入队友、传递、双打专属牌。
- 每次补机制都要同步补固定场景，否则后续很难判断是真实规则差异还是旧 bug。

## 十一、完成后的下一步

当本阶段完成并测试通过后，下一步进入“三本机制池第一组：亡语与召唤”。

开始三本前必须先确认：

- 回放调试器能清楚展示一次完整战斗。
- 对手战场能快速构造指定站位。
- 保存场景能稳定复现。
- 一本、二本代表场景在可视化回放中与预期一致。
- 官方 API 入口已经在文档中明确，后续查真实卡牌文本时优先使用官方数据源。
