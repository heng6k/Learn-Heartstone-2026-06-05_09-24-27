# 上线后产品总体路线

> 状态：当前产品阶段路线
> 制定日期：2026-07-30
> 范围：规则版本更新、新手一图流、纯残局、肉鸽爬塔和在线 1v1
> 当前动作：先由项目负责人发布已制作的视频和网站，功能实现暂不启动

## 1. 当前起点

项目已经完成源码分层、内容协议、Remote → LKG → Embedded 回退、ReleaseCandidate、Vercel Preview/Promote、Production、自定义域名和安全基线。当前正式入口为 <https://jsoncool.com/>。

接下来的第一步不是立即修改代码，而是：

1. 把已经制作好的视频和网站发布到社交媒体。
2. 对外明确当前是 Alpha 训练与模拟工具。
3. 收集用户最先遇到的理解、操作、规则版本和残局需求。
4. 发布动作完成后，再冻结 R1 新版本规则的精确范围。

本路线不把多个大功能塞进同一个版本。每个阶段只验证一个主要产品假设，并且必须按照 [PatchSubmissionAndReleasePolicy.zh-CN.md](PatchSubmissionAndReleasePolicy.zh-CN.md) 独立发布和回滚。

## 2. 产品发展主线

```text
R0 社交发布与反馈
        ↓
R1 跟进酒馆战棋新规则版本
        ↓
R2 场景底座 + 新手一图流
        ↓
R3 纯残局（明牌 / 信息受限）
        ↓
R4 残局肉鸽爬塔
        ↓
R5 共享酒馆在线 1v1
```

对应的用户价值是：

```text
知道这个工具 → 能直接上手 → 能专项练习 → 愿意重复挑战 → 愿意真人对抗
```

## 3. 路线原则

1. **规则准确先于新模式**：先让基础规则和内容跟上当前酒馆战棋版本，再在其上制作教程和残局。
2. **共用底座先于内容堆量**：新手、残局和肉鸽必须共用场景定义、目标、可见性、随机种子、结算与解释能力。
3. **纯残局先于肉鸽**：先用可控的单局内容证明场景底座正确，再引入跨回合奖励、随机事件和存档。
4. **本地原型先于联机后端**：在线 1v1 先验证共享酒馆规则与确定性，再建设权威服务器、房间和重连。
5. **每个阶段独立发布**：规则更新、新手、残局、肉鸽和联机不能捆绑成一次无法定位问题的大版本。
6. **默认不停服**：旧 Production 服务用户，新版本在 Preview 验收后原子 Promote。
7. **不提前承诺日期**：阶段只有进入条件和退出条件，发布日期根据真实反馈、规则范围和测试证据决定。

## 4. 阶段总览

| 阶段 | 核心目标 | 主要交付 | 前置依赖 | 退出条件 |
| --- | --- | --- | --- | --- |
| R0 | 让真实用户看到现有产品 | 社交视频、网站链接、Alpha 说明、反馈入口 | 当前 Production | 已发布并取得首轮可分类反馈 |
| R1 | 跟进当前酒馆战棋版本 | 新规则、内容版本、兼容门禁与发布记录 | 官方版本范围核对 | 新规则相关测试和完整发布门禁通过 |
| R2 | 让新手在固定情境中直接上手 | Scenario/Challenge 底座、新手一图流、固定教学场景 | R1 稳定规则基线 | 新手能在少量引导内完成指定正规阵容目标 |
| R3 | 建立核心残局训练能力 | 明牌残局、信息受限残局、多种目标与解释 | R2 场景底座 | 两种信息模式均可复现、结算和解释 |
| R4 | 提供可重复游玩的单人内容 | 肉鸽爬塔、回合增益、饰品/畸变、分支与存档 | R3 稳定残局 | 一次完整爬塔可保存、恢复、结算并复现 |
| R5 | 提供共享酒馆真人残局对抗 | 双人原型、房间、权威状态、每回合对战和扣血 | R3 与 R4 均稳定、在线架构批准 | 双方一致、可重连、可结算的封闭测试完成 |

## 5. 共用场景与挑战底座

R2–R4 不应各自实现一套关卡系统。建议共用以下概念：

### 5.1 `ScenarioDefinition`

一个可复现情境至少包含：

- `scenarioId`、`schemaVersion`、标题、难度和标签。
- 客户端版本、规则版本和内容版本。
- 固定随机种子或允许的种子集合。
- 当前回合、双方血量/护甲、金币和酒馆等级。
- 我方阵容、手牌、酒馆、冻结状态和已激活机制。
- 对手阵容或允许公开的对手摘要。
- 允许操作、禁止操作、回合限制和完成目标。
- 成功、失败、部分完成条件以及提示/解释。

### 5.2 `VisibilityPolicy`

对手信息不应由 UI 临时隐藏，而应作为场景规则：

- `Full`: 完整显示对手阵容、站位和属性。
- `LimitedScout`: 只显示对手酒馆等级、随从数量和允许公开的属性摘要。
- 后续如需“上一战斗已知信息”或“侦察到的局部信息”，在同一策略中扩展。

### 5.3 `ChallengeObjective`

同一个情境可以具有不同目标：

- 构成指定正规阵容。
- 在限定回合内完成操作。
- 本回合获胜或避免死亡。
- 最小化承受伤害。
- 最大化对手受到的伤害。
- 在多个随机种子下达到目标胜率。
- 使用限定金币、酒馆等级或操作次数完成。

### 5.4 `RuleModifier`

肉鸽和特殊残局通过组合式修正器扩展，不把规则散落在关卡代码中：

- 每回合额外金币或经济规则。
- 酒馆等级上限、下限或升级成本。
- 可用种族、随从池和商店限制。
- 饰品、畸变、任务、奖励或特殊全局效果。
- 战斗伤害倍率、回合上限和恢复规则。

### 5.5 可复现与解释

- 每个场景和结果必须携带规则/内容版本与随机种子。
- 系统不仅给出成功或失败，还要解释关键操作、触发和差异。
- 场景导出不得依赖本机绝对路径或用户隐私信息。
- 后续共享、题库和联机记录继续复用同一版本兼容字段。

## 6. R0：社交媒体发布与首轮反馈

### 目标

让真实玩家理解产品现在能做什么，并判断后续功能的真实优先级。

### 当前行动

- 发布已制作的视频并附 <https://jsoncool.com/>。
- 明确写明 Alpha、当前玩法定位和已知边界。
- 不承诺尚未冻结范围的发布日期。
- 保留一个稳定的反馈入口，至少能取得浏览器、版本、复现步骤和截图。

### 建议观察

- 用户是否能独立进入并完成一次基础模拟。
- 用户首先询问的是规则版本、新手引导、残局还是分享。
- 哪些 UI 操作最妨碍使用。
- 是否出现特定浏览器、网络或移动端问题。
- 评论中的功能愿望和真正阻断问题应分开记录。

### 退出条件

- 视频和网站已经发布。
- 首轮反馈能够分为规则、可用性、Bug、新手、残局和其他需求。
- 没有需要先回滚或紧急修复的 P0/P1 线上事故。

## 7. R1：跟进酒馆战棋新版本

### 目标

先建立可信的新规则基线，不同时引入新手、残局、肉鸽或联机代码。

### 实施范围

- 核对官方新版本的随从池、数值、关键词、英雄/伙伴、饰品、畸变和系统规则变化。
- 将规则、模型和效果放入 `Runtime/Domain`；流程编排放入 `Runtime/Application`。
- 数据解析和内容交付继续使用现有 `Adapters` 与 Remote → LKG → Embedded。
- 纯数据变化发布新的 `contentVersion`；需要新客户端代码时同时提升客户端版本和 `requiredClientVersion`。
- 现有客户端已经理解的文案、数值和随从池变化按 `CONTENT` 处理；客户端无法理解的新机制、字段或流程按 `CLIENT/FEATURE` 处理并提升 minor 版本。
- 为新增和变化机制补直接测试，再进入普通 EditMode、Stress（排除 Marathon）、PlayMode 和 WebGL 发布门禁。

### 明确不做

- 不在同一个版本中顺带实现完整新手模式。
- 不顺带加入残局题库或肉鸽流程。
- 不因官方更新而覆盖已经发布的内容版本字节。
- 不先承诺版本号为 `1.0.1`；如果当前仍是 `0.1.0-alpha`，重大规则更新通常应使用新的 minor Alpha。

### 退出条件

- 新旧规则差异有清单和实现状态。
- 所有新增规则有自动化证据和玩家旅程验收。
- 新内容/客户端兼容关系已验证。
- Preview 和 Production 来自同一候选且可以回滚。

## 8. R2：场景底座与新手一图流

### 产品形态

用户打开一个入口，就能看到固定情境、当前目标、允许操作和完成结果，不需要先理解整个自由模拟器。

“一图流”不是静态攻略图片，而是一屏内完成的交互式教学：

- 上方说明当前局面和目标。
- 中间直接展示需要操作的酒馆/阵容。
- 侧边或下方显示少量关键提示。
- 完成后解释为什么这样操作能形成正规阵容或正确节奏。

### 第一批内容建议

- 基础买、卖、刷新、冻结和升本。
- 构成一个指定种族的正规阵容骨架。
- 三连、发现和阵容转型的固定情境。
- 经济与战力之间的基础取舍。
- 嘲讽、圣盾、亡语和关键随从保护站位。

### 工程交付

- `ScenarioDefinition`、目标、提示、结算和版本兼容。
- 可由数据创建场景的 Editor/校验工具。
- 固定种子和可重复运行测试。
- 独立入口，不把教程藏在自由模拟器设置中。
- 首批 5–10 个高质量场景；先验证理解，不追求数量。

### 退出条件

- 用户无需外部说明即可进入场景、理解目标并完成操作。
- 错误操作会得到原因和改进建议，而不只是“失败”。
- 场景可导出、重载和在相同版本下复现。
- 至少完成一次真实新手观察测试。

## 9. R3：纯残局训练

### 模式 A：明牌残局

- 完整显示双方阵容、站位和属性。
- 重点训练站位、买卖、刷新、升本、换阵容和资源分配。
- 支持固定种子和多种子结果分布。

### 模式 B：信息受限残局

- 只显示对手酒馆等级、随从数量和规则允许的属性摘要。
- 不直接暴露完整对手阵容，模拟真实后期侦察与推断。
- 玩家需要在有限信息下决定站位、针对牌、经济和战力投入。

### 题目结构

- 当前局面与剩余回合。
- 可见信息及其来源。
- 可调整区域和操作限制。
- 胜利、存活、伤害或胜率目标。
- 参考答案、关键分支和解释。

### 退出条件

- 两种可见性策略不依赖临时 UI hack。
- 同一道题可以稳定复现并输出结果摘要。
- 明牌和信息受限题都能解释关键决策。
- 题目数据携带规则、客户端、内容版本和随机种子。

## 10. R4：残局肉鸽爬塔

### 产品形态

玩家从一个基础残局配置开始，连续完成多层挑战。每回合或每层获得不同增益、限制和分支选择，形成可重复游玩的单人模式。

### 可组合内容

- 每回合额外金币、利息或出售收益变化。
- 酒馆等级限制、升级成本或商店刷新规则。
- 饰品、畸变、任务、奖励和临时全局效果。
- 随从池、种族、手牌、血量和战斗伤害修正。
- 精英层、恢复层、商店层和随机事件。
- 固定每日种子或可分享挑战种子。

### 必须新增的跨局能力

- `RunState`：当前层数、资源、增益、限制和随机状态。
- 保存与恢复：浏览器刷新后可继续，版本不兼容时明确提示。
- 奖励选择与分支路径。
- 一次完整爬塔的结算、失败原因和复盘摘要。
- 内容创作和数值校验工具，避免所有关卡硬编码。

### 明确不做

- R4 不同时实现实时联机。
- 不在场景底座不稳定时堆大量随机修正器。
- 不用无法复现的全局随机数驱动爬塔。

### 退出条件

- 至少一条完整爬塔路线可以开始、保存、恢复、结算和重放关键结果。
- 增益与限制通过组合式修正器实现，并有冲突校验。
- 同一种子、版本和选择序列可以复现。

## 11. R5：共享酒馆在线 1v1 残局

### 目标玩法

- 双方互相知道彼此的公开状态。
- 双方共用同一个酒馆随从池或商店来源。
- 每回合各自完成招募操作后进行双方战斗。
- 战斗按真实酒馆战棋方式结算伤害并持续到一方失败。

### R5A：本地确定性双人原型

先在不联网的情况下确定：

- 双方操作是轮流、同时还是带计时窗口。
- 共享酒馆如何刷新和分配。
- 双方购买同一资源时的顺序与冲突规则。
- 战斗种子、伤害、回合推进和胜负是否完全一致。
- 哪些状态必须由权威端决定。

只有本地原型可重复、规则得到认可后，才进入服务器阶段。

如果共享状态、冲突顺序和战斗确定性尚未先定型，直接建设服务端会把产品歧义固化成网络协议，造成双方状态分叉和后端重做。

### R5B：权威在线房间

服务端至少负责：

- 房间码、加入、准备、回合计时和状态机。
- 共享酒馆、购买、出售、刷新、冻结和升级的权威顺序。
- 双方阵容快照、战斗种子、结果和扣血。
- 断线重连、超时托管、重复请求幂等和版本拒绝。
- 最小审计日志，防止客户端直接修改金币、商店或阵容。

客户端只提交意图并展示权威结果，不能成为共享状态真源。

### R5C：封闭测试

- 先使用邀请房间，不立即做公开匹配。
- 先支持同版本客户端，不急于跨版本联机。
- 先验证稳定性、重连和状态一致，再考虑排行榜、观战和复杂反作弊。

### 退出条件

- 两端对共享酒馆、阵容、战斗和血量始终一致。
- 断线后能恢复到权威快照。
- 重复或过期操作不会重复扣费或推进回合。
- 一场完整 1v1 可以在封闭环境中结束并生成复盘证据。

## 12. 版本与发布映射

路线使用 R0–R5，不把阶段号直接等同于语义化版本。每个阶段开始前根据当前 Production 决定版本号：

| 变化 | 推荐版本动作 |
| --- | --- |
| 兼容小 Bug | 提升客户端 patch，例如 `0.1.1-alpha` |
| 新酒馆规则或显著新模式 | 提升客户端 minor，例如 `0.2.0-alpha` |
| 纯兼容内容 | 客户端可不变，发布新 `contentVersion` |
| 内容需要新代码 | 同时提升客户端版本、`requiredClientVersion` 和 `contentVersion` |
| 正式 1.0 后的不兼容变化 | 再评估 major 版本 |

每个阶段仍按补丁规范经过 ReleaseCandidate、Preview、smoke、Promote 和回滚点保留。

## 13. 阶段进入门槛

开始下一阶段前必须满足：

- 上一阶段已经有可复核的完成证据，不只是代码“看起来完成”。
- 当前 Production 没有未收敛的 P0/P1。
- 新阶段的范围、非目标、版本和测试门禁已经冻结。
- 现有用户反馈支持继续该方向，或项目负责人明确批准战略投入。
- 不会把用户工作树中的无关改动、生成物或视频工程混入功能提交。

## 14. 主要风险与控制

| 风险 | 控制方式 |
| --- | --- |
| 官方版本持续变化，规则追赶没有终点 | R1 冻结一个明确版本快照；后续变化走独立补丁 |
| 新手、残局和肉鸽各写一套场景系统 | R2 先建立共用 Scenario/Challenge 契约，后续只组合扩展 |
| 残局结果不可解释或不可复现 | 固定版本与种子，输出关键操作和触发摘要 |
| 肉鸽修正器组合爆炸 | 组合式修正器、冲突规则、内容校验和有限首发池 |
| 在线 1v1 状态不一致 | 本地确定性原型先行，服务器权威，客户端只提交意图 |
| 后端成本和国内网络不稳定 | 封闭房间 MVP，先验证使用价值，再确定长期基础设施 |
| 多个阶段捆绑导致无法回滚 | 每阶段独立版本、独立候选和独立 Production 回滚点 |
