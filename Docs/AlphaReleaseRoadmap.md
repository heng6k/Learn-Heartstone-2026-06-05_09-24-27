# 酒馆战棋训练器 Alpha 发行路线与渠道投放计划

## 目标定位

这个项目第一阶段不应以“完整新手教程”或“完整战棋复刻”对外承诺，而应定位为：

> 一个用于酒馆战棋练习、复盘、站位验证和残局构造的 Alpha 沙盒工具。

当前版本已经能模拟核心酒馆战棋环境，并且经过了极端身材和长战斗压力测试。它现在最适合先拿到真实用户反馈，验证以下问题：

- 用户是否愿意用它复盘或构造局面。
- 哪些 UI 操作最阻碍使用。
- 用户更需要新手教程、残局训练、战斗复盘，还是机制验证。
- 哪些英雄、宝宝、机制缺口会真正影响用户留下来。
- 用户是否愿意分享场景、截图、复盘结果或问题反馈。

## 发行原则

1. **先发 Alpha，不等完美**
   - 现在的价值在于“能模拟、能复盘、能验证”，不是“UI 漂亮、教程完整”。
   - 先通过小范围真实用户判断产品方向，避免闭门继续补功能。

2. **每一版只验证一个核心假设**
   - v0.1 验证是否有人愿意使用模拟器。
   - v0.2 验证反馈与问题复现链路。
   - v0.3 验证复盘/分享是否能形成传播。
   - v0.4 验证新手教程是否能帮助留存。
   - v0.5 验证残局训练是否能形成核心卖点。

3. **公开承诺要克制**
   - 不说“完整实现全部英雄/宝宝”。
   - 不说“100% 官方一致”。
   - 对外说清楚这是 Alpha，重点是训练、复盘和模拟。

4. **发放渠道从低风险到高曝光**
   - 先发给熟人、群友、核心玩家。
   - 再发到 B 站、社区、贴吧/论坛。
   - 最后再考虑 itch.io、官网、Steam 等正式分发平台。

5. **先建立反馈闭环，再扩大用户量**
   - 早期用户太多不是好事。如果没有反馈收集、版本号、问题复现，用户越多越混乱。

## 版本节奏总览

| 版本 | 阶段名称 | 核心目标 | 主要用户 | 是否公开 |
| --- | --- | --- | --- | --- |

## v0.1 Alpha 种子版

### 主要目的

验证最基础的问题：即使 UI 粗糙、教程未完成，是否仍有人愿意用这个工具模拟战斗、试站位、复盘思路。

### 这一版不追求什么

- 不追求 UI 美观。
- 不追求完整新手教程。
- 不追求所有英雄/宝宝完全精准。
- 不追求大规模传播。

### 必须做的实际操作

1. **打包一个 Windows 可运行版本**
   - 版本号：`v0.1.0-alpha`
   - 文件名建议：`BattlegroundsTrainer_v0.1.0_alpha_win.zip`
   - 包内包含：
     - 可执行文件。
     - `README_使用说明.md`
     - `KNOWN_ISSUES_已知问题.md`
     - `CHANGELOG_更新记录.md`
     - `FEEDBACK_反馈说明.md`

2. **写清楚产品定位**
   - 启动页或 README 第一屏写：
     - 当前是 Alpha。
     - 当前主打模拟、复盘、站位测试。
     - 新手教程、残局处理、UI 美化还在后续计划中。

3. **准备 5-10 个示例场景**
   - 示例场景不要追求复杂，重点是让用户打开就知道能干什么。
   - 建议包含：
     - 圣盾/剧毒交互。
     - 嘲讽与站位。
     - 低攻高血长战斗。
     - 三连和发现。
     - 经济节奏测试。
     - 英雄技能和宝宝联动示例。

4. **准备反馈入口**
   - 最低要求：README 里写清楚反馈格式。
   - 更好做法：游戏内加“复制反馈信息”按钮。
   - 反馈信息至少包含：
     - 版本号。
     - 随机种子。
     - 玩家阵容。
     - 对手阵容。
     - 最近战斗日志。
     - 用户描述的问题。

5. **写已知问题**
   - UI 不方便。
   - 部分英雄/宝宝效果仍是近似或代理实现。
   - 当前没有完整新手教程。
   - 当前没有残局题库。
   - 个别复杂机制还不完全等同官方。

### 发放到哪里

#### 第一优先级：熟人和小群

适合渠道：

- 你自己的朋友。
- 熟悉酒馆战棋的 QQ 群/微信群。
- 愿意认真反馈的玩家小圈子。

优点：

- 反馈质量高。
- 用户更能容忍粗糙 UI。
- 出问题不会造成大范围负面印象。
- 方便你追问“你当时怎么操作的”。

缺点：

- 用户量有限。
- 反馈可能偏熟人视角，不够真实。

操作方式：

1. 发一个简短说明。
2. 附下载链接。
3. 附反馈格式。
4. 明确说：“这是 Alpha，主要想听复盘/模拟这件事有没有价值。”

示例文案：

```text
我做了一个酒馆战棋训练/复盘工具 Alpha 版，现在还没有完整新手教程，UI 也比较粗糙，但已经能构造局面、模拟战斗、测试站位和部分英雄宝宝效果。

这版主要想找愿意试用的人帮忙看三件事：
1. 模拟和复盘有没有用；
2. 哪些操作最不方便；
3. 哪些机制缺口最影响使用。

如果遇到问题，麻烦按这个格式反馈：版本号 + 你想做什么 + 出了什么问题 + 截图/阵容/日志。
```

### v0.1 放行标准

- 能在至少 2 台不同 Windows 机器上正常打开。
- 能完成一次编辑阵容、开始战斗、查看结果。
- 没有启动即崩溃。
- 没有明显的无限战斗卡死。
- README 和已知问题文档齐全。
- 至少发给 10-20 个种子用户。

### v0.1 观察指标

- 有多少人成功打开。
- 有多少人完成第一次战斗。
- 有多少人愿意反馈。
- 最常见的 5 个卡点是什么。
- 用户自发问的是“怎么用”，还是“为什么这里机制不对”。

## v0.2 Alpha 反馈版

### 主要目的

把反馈链路做扎实，让用户提出的问题可以被复现、分类和修复。

### 必须做的实际操作

1. **游戏内增加反馈导出**
   - 一键复制：
     - 版本号。
     - 当前回合。
     - 随机种子。
     - 玩家英雄。
     - 玩家阵容。
     - 对手阵容。
     - 最近战斗日志。
     - 是否触发 SafetyStopped。

2. **建立问题分类**
   - 崩溃。
   - UI 不会用。
   - 机制不一致。
   - 英雄/宝宝问题。
   - 战斗结果不符合预期。
   - 新手看不懂。
   - 建议功能。

3. **维护公开已知问题**
   - 把用户反馈过但暂未修的问题列出来。
   - 对每个问题写：
     - 当前表现。
     - 影响程度。
     - 临时绕过方式。
     - 后续计划。

4. **补最小 UI 可用性**
   - 不做大改版，只解决最痛点：
     - “开始战斗”更明显。
     - “编辑我方阵容/对方阵容”更明确。
     - “清空/重置/保存”按钮可见。
     - 战斗日志入口可见。

### 发放到哪里

#### 第二优先级：核心玩家社区的小范围帖

适合渠道：

- NGA 酒馆战棋相关版面。
- 旅法师营地相关讨论区。
- 百度贴吧酒馆战棋吧/炉石相关吧。
- B 站动态或专栏。

优点：

- 核心玩家多。
- 机制反馈质量高。
- 容易发现真实战斗逻辑缺口。

缺点：

- 用户更挑剔。
- UI 粗糙会被直接指出。
- 如果定位没写清楚，容易被当成“未完成品”批评。

操作方式：

1. 不要标题党。
2. 标题要明确 Alpha 和用途。
3. 主贴写清楚当前不是什么。
4. 放截图和短视频。
5. 反馈格式放在最上面。

建议标题：

```text
做了一个酒馆战棋复盘/模拟工具 Alpha，想找玩家帮忙测试站位和战斗复现
```

不建议标题：

```text
我做了一个完整酒馆战棋模拟器
```

### v0.2 放行标准

- 至少修复 v0.1 中最严重的 5 个问题。
- 反馈导出可用。
- 已知问题文档更新。
- 至少 30 条有效反馈被分类。
- UI 主流程可以在 1 分钟内被新用户摸懂。

## v0.3 复盘分享版

### 主要目的

让这个工具从“自己玩”变成“可以分享和讨论”。这一步比新手教程更适合先做，因为复盘和残局讨论更容易在社区传播。

### 必须做的实际操作

1. **场景保存**
   - 保存当前玩家阵容、对手阵容、英雄、酒馆状态、随机种子。
   - 文件格式可以先用 JSON。

2. **场景导入**
   - 用户可以导入别人分享的场景。
   - 导入失败要有错误提示。

3. **分享码或分享文件**
   - 短期可以先用文件。
   - 后续再做压缩分享码。

4. **战斗结果摘要**
   - 显示：
     - 胜负。
     - 战斗步数。
     - 是否 SafetyStopped。
     - 关键死亡顺序。
     - 关键触发列表。

5. **复盘说明文本**
   - 用户可以给场景写备注：
     - “这个局面我想验证左置嘲讽是否更好。”
     - “这个残局我不知道该不该换站位。”

### 发放到哪里

#### B 站

适合形式：

- 1-3 分钟演示视频。
- 动态附下载。
- 后续用真实案例做系列视频。

优点：

- 演示型工具很适合视频传播。
- 用户能直观看到用途。
- 方便积累关注。

缺点：

- 需要录屏和剪辑。
- 视频质量差会影响第一印象。

操作建议：

- 第一个视频不讲技术。
- 只展示三个场景：
  - 编辑阵容。
  - 开始战斗。
  - 保存并分享复盘。
- 视频标题突出“复盘”和“站位验证”。

建议标题：

```text
我做了一个酒馆战棋复盘工具：可以自己摆阵容测试站位
```

#### QQ 群/微信群

适合形式：

- 发分享场景。
- 让群友讨论“这个站位怎么摆”。

优点：

- 互动快。
- 容易形成小范围讨论。

缺点：

- 内容沉淀差。
- 文件容易过期。

#### NGA/贴吧/旅法师营地

适合形式：

- 发“复盘案例帖”。
- 不只是发工具，而是发一个局面让大家讨论。

优点：

- 讨论深。
- 容易发现产品真实价值。

缺点：

- 对机制准确性要求更高。

### v0.3 放行标准

- 能保存和导入至少 10 个测试场景。
- 不同机器之间场景文件能互相打开。
- 用户能通过文件复现同一场战斗。
- 至少产生 5 个来自用户的真实复盘场景。

## v0.4 新手教程 MVP

### 主要目的

开始解决项目最初想解决的问题：酒馆战棋新手教程不足。

这一版不要做成长篇百科，而要做任务式训练。

### 教程结构建议

1. **基础操作**
   - 买随从。
   - 卖随从。
   - 升酒馆。
   - 刷新酒馆。
   - 冻结酒馆。

2. **战斗理解**
   - 攻击顺序。
   - 嘲讽。
   - 圣盾。
   - 剧毒/烈毒。
   - 亡语。
   - 风怒。

3. **经济节奏**
   - 什么时候升本。
   - 什么时候买战力。
   - 什么时候找三连。

4. **站位训练**
   - 嘲讽放哪。
   - 关键随从保护。
   - 亡语随从位置。
   - 防狂战/溅射/切后排。

5. **复盘训练**
   - 为什么输了。
   - 是战力不够、站位不对，还是运营落后。

### 必须做的实际操作

1. **做任务系统**
   - 每个任务有目标、操作步骤、完成条件。
   - 示例：
     - “买一个随从并放上场。”
     - “调整站位让圣盾随从先攻击。”
     - “构造一个三连并选择奖励。”

2. **做教学场景**
   - 不依赖随机发牌。
   - 每个场景固定阵容。
   - 用户操作后能看到结果。

3. **做反馈说明**
   - 用户做错时不要只说失败。
   - 要解释：
     - 错在哪里。
     - 为什么。
     - 可以怎么改。

4. **教程入口独立**
   - 不要把教程藏在普通模拟器里。
   - 首页直接有：
     - 自由模拟。
     - 新手教程。
     - 复盘/残局。

### 发放到哪里

#### B 站新手向内容

适合形式：

- “用一个工具讲懂酒馆战棋站位”。
- “新手最容易犯的 5 个错误”。

优点：

- 新手更容易从视频进入。
- 教程功能适合演示。

缺点：

- 需要你把教学内容讲清楚。

#### 小红书/抖音

适合形式：

- 短视频切片。
- 每条只讲一个知识点。

优点：

- 有机会触达非核心论坛用户。

缺点：

- 用户下载 PC 工具的转化可能低。
- 评论质量可能不如核心社区。

#### TapTap/好游快爆

当前不建议作为主渠道。

原因：

- 如果项目是 Windows 工具，不是移动端游戏，这些平台匹配度不高。
- 用户预期可能是“能直接玩”，而不是“训练器”。
- 可以后续作为内容曝光渠道，不建议 v0.4 前投入太多。

### v0.4 放行标准

- 至少 10 个教程任务。
- 完整新手能按教程完成基础战斗流程。
- 每个教程任务都有成功/失败反馈。
- 至少 5 个真实新手完成测试。

## v0.5 残局训练版

### 主要目的

做出最容易传播的产品形态：残局题、站位题、复盘挑战。

这会比“完整模拟器”更容易让用户转发，因为用户可以发一道题：

> 这个局面怎么站位胜率最高？

### 必须做的实际操作

1. **残局题库**
   - 每道题包含：
     - 我方阵容。
     - 对手阵容。
     - 可调整区域。
     - 固定随机种子或多种随机种子。
     - 目标：胜利、减少伤害、提高胜率。

2. **答案解释**
   - 不只告诉用户对错。
   - 解释为什么这个站位更好。

3. **多次模拟**
   - 对同一局面跑多个随机种子。
   - 给出胜率或结果分布。

4. **排行榜或分享**
   - 早期可以先不做账号系统。
   - 可以分享：
     - 题目文件。
     - 结果截图。
     - 最优站位截图。

### 发放到哪里

#### B 站和社区最适合

适合形式：

- 每周一道残局题。
- 评论区收答案。
- 下一期公布工具模拟结果。

优点：

- 容易形成互动。
- 能自然宣传工具。
- 用户不一定先下载，也能参与。

缺点：

- 需要持续产出题目。

#### 论坛/贴吧/NGA

适合形式：

- 发题目帖。
- 让玩家讨论不同站位。
- 附工具下载和场景文件。

优点：

- 高质量讨论。
- 能快速暴露模拟器机制问题。

缺点：

- 如果答案和玩家直觉冲突，需要解释足够清楚。

### v0.5 放行标准

- 至少 20 道残局/站位题。
- 每道题可导入复现。
- 至少支持同一题跑 20-100 个种子做结果分布。
- 能导出结果截图或文字摘要。

## v1.0 正式产品版

### 主要目的

当产品已经证明有人用、有人反馈、有人分享后，再进入正式产品化。

### 必须具备

- 主要 UI 重做。
- 清晰首页。
- 自由模拟、教程、复盘、残局四个入口。
- 场景保存/导入/分享稳定。
- 错误反馈和日志导出稳定。
- 已知问题和版本说明维护稳定。
- 至少一个稳定发布页。

### 可考虑的正式分发渠道

#### itch.io

推荐优先级：高。

适合原因：

- 对独立工具友好。
- 上传 Windows 包简单。
- 支持版本更新。
- 可以写完整介绍、截图、更新日志。
- 用户下载门槛低。

风险：

- 国内访问和下载体验不一定稳定。
- 需要同时准备国内网盘镜像。

适合阶段：

- v0.3 以后可以开始。

#### GitHub Releases

推荐优先级：中。

适合原因：

- 版本管理清楚。
- 适合技术用户和长期归档。
- 方便 issue 反馈。

风险：

- 普通玩家不一定会用 GitHub。
- 国内访问可能不稳定。

适合阶段：

- v0.2 以后可以作为备份发布源。

#### 独立官网/落地页

推荐优先级：中高。

适合原因：

- 最能控制产品表达。
- 可以放下载、视频、教程、更新日志、反馈入口。
- 后续可以做 SEO。

风险：

- 需要额外维护。
- 早期可能没必要做复杂。

适合阶段：

- v0.3 或 v0.4 后开始做一个简单页面。

#### Steam

推荐优先级：低，后期再考虑。

适合原因：

- 分发稳定。
- 用户信任度高。
- 更新机制成熟。

风险：

- 上架成本和审核成本更高。
- 对 UI、美术、完成度要求更高。
- 涉及炉石相关内容时，IP 和商标风险更明显。

适合阶段：

- v1.0 后再评估。

#### Microsoft Store

推荐优先级：低。

适合原因：

- Windows 用户下载方便。

风险：

- 打包、审核、证书、商店规范都增加成本。
- 早期用户增长帮助有限。

适合阶段：

- 正式版稳定后再考虑。

#### 百度网盘/阿里云盘

推荐优先级：高，但只作为镜像。

适合原因：

- 国内用户下载方便。
- 分享门槛低。

风险：

- 版本管理混乱。
- 文件过期或被转存后无法控制。
- 用户对陌生 exe 有安全顾虑。

操作建议：

- 每个版本单独文件夹。
- 文件名带版本号。
- README 写校验信息。
- 不作为唯一下载源。

## 每次发行前检查清单

### 功能检查

- 能启动。
- 能编辑我方阵容。
- 能编辑对手阵容。
- 能开始战斗。
- 能查看战斗结果。
- 能查看或复制战斗日志。
- 能保存/导入场景，如果该版本支持。
- 已知问题没有新增严重崩溃。

### 测试检查

- 跑 `StressTests`。
- 跑关键 EditMode 测试。
- 如果涉及数值/战斗底层，跑 `RobustnessEdgeTests`。
- 重大版本前跑一次 30 分钟 soak。
- 记录测试结果到更新日志。

### 文档检查

- README 更新。
- CHANGELOG 更新。
- 已知问题更新。
- 反馈格式更新。
- 当前版本定位写清楚。

### 分发检查

- 包名带版本号。
- 下载链接可访问。
- 解压后目录结构清楚。
- 第一次启动说明清楚。
- 反馈入口可见。
- 截图和演示视频准备好。

### 发布后 24 小时操作

- 收集所有反馈。
- 标记 P0/P1 问题。
- 如果有启动崩溃，立即发 hotfix。
- 如果是机制争议，先记录复现，不急着口头解释。
- 如果是 UI 看不懂，优先改入口文案或操作路径。

### 发布后 72 小时操作

- 汇总前 20-50 条反馈。
- 更新已知问题。
- 决定下一版只修什么。
- 不要被零散建议带跑，先看重复出现的问题。

### 发布后 7 天操作

- 复盘：
  - 有多少人下载。
  - 有多少人成功打开。
  - 有多少人反馈。
  - 哪个功能被提到最多。
  - 哪个操作最卡。
  - 用户是在用它复盘、教程，还是单纯试玩。

## 反馈优先级

| 优先级 | 类型 | 处理方式 |
| --- | --- | --- |
| P0 | 启动崩溃、无法进入主流程、严重卡死 | 立即修，必要时撤回版本 |
| P1 | 战斗结果明显错误、数据丢失、无法复现反馈 | 下一版优先修 |
| P2 | UI 难用、路径不清楚、日志看不懂 | 每版持续改 |
| P3 | 单个英雄/宝宝机制不精准 | 进入缺陷文档，按影响排序 |
| P4 | 美术、动效、细节体验 | UI 重做阶段集中处理 |

## 当前最推荐的下一步

下一步不是继续补全所有英雄，也不是立即重做全 UI，而是做 **v0.1 Alpha 种子版发布包**。

### v0.1 Alpha 功能冻结记录

冻结日期：2026-06-20。

冻结目标：把当前训练器、英雄/伙伴基础效果、卡池版本控制和核心战斗流程收口到可测试、可发给种子用户的状态。

冻结期间只允许做以下工作：

1. 修复 P0/P1 阻塞问题：启动崩溃、无法进入主流程、测试全红、卡池配置无法保存或进入对局失效。
2. 修复明显坏体验：用户能看见但容易误操作的保存状态、弹窗提示、入口路径、缺图定位、日志可读性。
3. 更新发版文档：README、已知问题、更新记录、反馈说明、示例场景和测试记录。
4. 跑测试和冒烟验证：全量 EditMode、卡池版本控制路径、进入对局后的买卖刷新/下一回合/战斗/日志路径。

冻结期间暂不做：

- 不新增英雄/伙伴机制。
- 不新增双打系统、传递、队友奖励或 BGDUO 行为。
- 不重做整体 UI。
- 不新增大规模素材系统。
- 不做正式分发平台接入。

解除冻结条件：v0.1-alpha 发布包完成、本地测试记录和已知问题文档齐全，并完成至少一次种子用户发放前检查。

### v0.1 发布包最小任务

1. 增加版本号显示。
2. 增加启动说明或 README。
3. 增加已知问题文档。
4. 增加反馈说明文档。
5. 准备 5-10 个示例场景。

7. 发给 10-20 个种子用户。

### 暂时不要做

- 不要立刻做完整新手教程。
- 不要立刻重做全部 UI。
- 不要立刻上 Steam。
- 不要继续无差别补全所有英雄/宝宝。
- 不要在没有反馈导出能力时大规模公开。

## 关键判断

当前项目已经有足够技术基础进入 Alpha。真正的问题不是“还能不能继续补功能”，而是：

> 用户是否真的需要这个工具，以及他们首先需要它解决复盘、教程、残局中的哪一个问题。

因此，最优路线是：

1. 先小范围发 v0.1。
2. 用真实反馈决定 v0.2 的修复顺序。
3. 用复盘分享能力做 v0.3。
4. 再开始做新手教程 v0.4。
5. 最后用残局训练形成可传播的核心产品。
