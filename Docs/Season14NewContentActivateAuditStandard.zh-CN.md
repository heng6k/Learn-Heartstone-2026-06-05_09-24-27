## 3. 测试证据模型

每个内容条目都必须有独立台账，并沿用项目 E0–E5 证据等级：

| 等级 | 必须证明 |
|---|---|
| E0 DataPresent | 生产 CardId/DBF、版本成员、星级/费用、普通/金色文本、图片、本地化、实现状态 |
| E1 LogicVerified | 正常效果、失败原子性、阶段、目标、次数、普通/金色、幂等、保存恢复 |
| E2 ViewVerified | 卡面/饰品/黑赐 HUD 显示权威状态；禁用原因、来源和变化可见 |
| E3 InteractionVerified | 真实 EventSystem 点击/拖拽/定向/取消；不使用 `onClick.Invoke()` 代替玩家输入 |
| E4 JourneyVerified | 从可访问入口完成选择、获得、触发、回合推进、战斗和回放 |
| E5 BuildVerified | Windows/WebGL 正式资源、关键分辨率、日志和 Player Build 验收 |

“一个条目在某测试文件中出现”只证明可追溯，不自动等于 E1；一个 carrier fixture 同时覆盖多张卡时，必须核对每张卡是否有独立结果与反向断言。

### 3.1 测试单位不是单卡，而是机制簇

越复杂的机制，越不能只在真空场景中测试该卡。每张复杂内容除单卡基础测试外，必须登记并验证与它发生真实规则交互的“配合卡集合”。

机制簇至少包含四种角色：

1. **机制载体**：实际拥有发动、进击、亡语、战吼、回合开始/结束、复生、抉择等效果的随从、饰品或黑暗之赐。
2. **放大器**：增加触发次数、重复效果、提高倍率或让多个分支同时结算的卡，例如布莱恩、瑞文戴尔男爵/提图斯、达卡莱附魔师及抉择双效果来源。
3. **改写器**：复制、变金、三连、变形、复生、重新召唤、转移绑定或改变来源实例的卡与系统。
4. **消费者/观察者**：监听该事件并获得收益的其他随从、饰品、任务或黑暗之赐，例如进击观察者、召唤计数、友方死亡计数和亡语重复来源。

单卡测试只回答“它单独能否工作”；机制簇测试必须回答：

- 配合卡加入后，谁应该额外触发，谁绝不能触发？
- 触发次数是相加、取最强、分别结算，还是明确不叠加？
- 普通与金色配合卡同时存在时，倍率和优先级是什么？
- 同一事件被重放、复制或恢复时，是否仍只结算应有次数？
- 来源离场、目标变更、三连换 InstanceId 后，观察者是否仍绑定正确对象？
- 战斗副本中的临时变化是否错误写回招募阶段，或永久成长是否错误丢失？

每个复杂条目的台账必须增加：`MechanicCluster`、`PartnerCards`、`InteractionRule`、`MustTrigger`、`MustNotTrigger`、`Ordering`、`EvidenceLevel`。没有配合卡组合证据时，即使单卡 E1 通过，也不能宣称该机制排查完成。

## 4. 三类重点矩阵

### 4.1 17 张发动随从

每张至少覆盖：

- 普通与金色成本、次数、目标和结果。
- 金币不足、次数耗尽、冷却、错误阶段、来源离场、无合法目标。
- 无目标、酒馆目标、友方目标、不能选择自身等不同目标形态。
- 多个发动随从同时在场时，各自按 `SourceInstanceId` 独立显示和结算。
- 三连、复制、变形、沉默/移除、存档恢复和 UI 重建后不串用次数或目标。
- 重复快速点击只消费一次；取消定向不扣费、不消耗次数。
- 招募日志、机制时间线和回放能解释“哪张随从发动了什么”。
- 每张发动随从必须至少进入一个真实配合卡场景；不能用同一个通用 resolver 测试替代 17 张各自的组合规则。

### 4.2 22 张五/六本高本随从

高本效果复杂、倍率高，至少补充：

- 普通/金色差异不是简单身材翻倍时的精确断言。
- 多次触发、最强倍率、叠加顺序和重放去重。
- 满手牌、满战场、召唤溢出、空酒馆、无目标和资源不足。
- 战吼、亡语、进击、施法、抉择、发现、磁力、复生等跨机制组合。
- 敌我侧隔离、战斗副本与永久招募状态隔离。
- 战斗回放和日志能解释触发来源、目标和最终状态。
- 每张高本随从必须按其主要机制配一组放大器/改写器/观察者测试；高本单卡测试不作为完成证据。

重点样例包括但不限于：泰瑞尔的定向发动及 40/40、80/80；守门融合怪的受法术触发；安静的投递员的特殊金色与三连奖励抑制；老牌恶匪的抉择双分支；进击/亡语/复生与黑暗之赐观察者的组合。

### 4.3 47 饰品与 43 黑暗之赐

每项至少覆盖：

- 候选池、费用/出现回合、条件过滤、选择、装备/绑定和替换。
- 绑定目标实例迁移：三连、复制、变形、出售/移除和存档恢复。
- TurnStarted、TurnEnded、CombatStarted、CardPlayed、RallyResolved、DeathrattleResolved 等触发各自只结算一次。
- 普通/金色、任务/饰品/黑赐之间的触发倍率、顺序与敌我隔离。
- 获得第三张随从的所有入口统一经过三连事务；黑赐与饰品不能绕过。
- UI 显示当前效果、来源、剩余次数/冷却和最近触发；回放与日志术语一致。

## 5. “发动”UI 的固定方向

“发动”操作改为出现在效果来源随从身上，不再以全局快捷/操作栏作为主要入口。

### 5.1 修复前问题（已关闭）

当前 `BuildSelectedRecruitActionButtons` 先读取选中的己方随从，再把 `UnityRecruitActionButton-*` 创建到全局操作栏。玩家必须先选卡，再把视线移到另一处操作；多个发动随从并存时，来源关系不够直接。

现有 UI 测试主要通过 `onClick.Invoke()` 驱动全局按钮；这属于组件层白盒，无法证明卡面入口在真实 EventSystem、遮挡、缩放和低分辨率下可用。现有 `PlayMode_PJ02_BasicRecruitActionsCompleteThroughRealInput` 测的是冻结、刷新、购买、打出、移动、出售和升本，没有测试随从“发动”。

### 5.2 目标交互

- 每个拥有发动能力的己方战场随从，在卡面范围内显示稳定的发动徽标/按钮。
- 卡面入口与该随从 `InstanceId` 直接绑定；点击后生成含 `SourceInstanceId` 的命令。
- 第一视觉层只显示“发动”与可用/已用状态；费用、剩余次数和目标要求可在徽标、悬停/选中详情中渐进展开。
- 可用、次数耗尽、冷却、金币不足、错误阶段、无合法目标使用图标、文字和明暗共同表达，不能只靠颜色。
- 定向开始后，来源随从保持明确高亮；合法/非法目标和取消路径清楚可见。
- 动画只表达刚刚发动、失败或次数变化；剩余次数和冷却是稳定状态，不持续闪烁。
- 全局栏可以保留选中随从的详情或快捷提示，但不再是唯一或主要入口。

### 5.3 UI 验收

- 两个以上发动随从同时在场，分别显示各自状态，点击 A 不会消耗 B。
- 普通/金色同名随从同时在场，成本与次数按实例正确。
- 994×384、1000×600、1280×720、1366×768、1920×1080 下不遮挡名称、攻血、关键词和卡图主体。
- 真实 Raycast 命中卡面按钮；拖拽、选卡、详情、发动不会互相误触。
- 取消、非法目标、快速连点、UI 重建、回放跳转和减少动态效果均有测试。
- 至少一条 L4 玩家旅程完成：将发动随从加入战场 → 从卡面发动 → 选择合法目标 → 观察资源/次数/效果/日志 → 推进回合确认重置或冷却。

### 5.4 2026-08-14 已落地实现与证据

- 每个己方战场发动随从都在自身卡面内创建独立按钮，身份直接绑定 `(SourceInstanceId, ActionId)`；按钮同时显示费用、剩余次数和“可用/已用/锁定原因”，不只依赖颜色。
- 卡面发动按钮不复用原“出售”按钮，出售路径保持不变；选中随从后的全局发动栏继续保留为辅助详情入口，但不再是唯一入口。
- 进入定向后，卡面与全局发动按钮暂时让出 Raycast，由合法目标卡接收点击；来源离场、能力变化或阶段变化时，pending 会取消并显示“发动来源已离场，已取消目标选择”，不会继续绑定旧实例。
- EditMode 聚焦门禁覆盖多 ActionId 独立记账、旧状态兼容、三连、出售、变形、回手再打出、锁定态、卡面按钮和 pending 取消，job `160cb57db8484ed7804b2b3d3c271c8e` 为 41/41 通过。
- PlayMode 以真实 `GraphicRaycaster + ExecuteEvents` 点击私家调查员卡面发动按钮，证明金币 5→4、状态写入、UI 重建后按钮变为 0/1 且禁用，job `3f8b09f2ba1e448a91b5cdb13946c72e` 为 1/1 通过。完整核心玩家旅程 job `0a9b2bede9ea44619837c9fc81431560` 为 17/18；唯一失败是既有机制库中英文文案断言，不经过发动链。
- 本节只关闭“卡面入口、状态归属和真实 Raycast”缺口；994×384 等全部目标分辨率、17 张逐卡完整目标链和 Build 级验收仍按 4.1 与 5.3 扩展，不能由一条玩家路径替代。

## 6. 已知根因与风险

1. 证据混级：目录、行为、View、真实输入和 Build 结果曾被合并成一个“已覆盖”。
2. 全局入口错位：随从动作被投影到全局栏，视觉归属与命令来源分离。
3. 监听器假通过：`onClick.Invoke()` 绕过可见性、遮挡和 Raycast。
4. 实例迁移风险：三连会创建新 InstanceId；黑赐过去已出现绑定旧实例而丢失的问题。
5. 获得入口分散：最新全项目审查已发现黑赐和反射吊坠获得第三张随从时漏三连。
6. 全量门禁不可信：2026-08-13 审查记录完整 Unity EditMode 长时间无最终结果；局部 393/393 或历史 2162/2162 不能替代当前全量门。

## 8. 2026-08-14 首批机制簇专项结果

执行环境：Unity `6000.4.10f1`、Unity Test Framework `1.6.0`，复用当前 Editor 的 Unity-MCP 精确测试入口。

### 8.1 已证明通过的新增组合

- 海藻护工 × 普通/金色布莱恩：普通与金色发动分别乘上战吼重复次数，四组倍率用例均通过。
- 两个私家调查员同时在场：`SourceInstanceId` 独立计次；同回合第二次拒绝且不扣费；下回合恢复。
- 泰瑞尔 × 多疑的监狱守卫：先设为 40/40 再加属性得到 43/43；先加属性再设值回到 40/40，顺序断言通过。
- 凶兆之石 × 黑暗之赐 × 第三张随从：真实选择入口立即三连，并把有效赐福绑定迁移到金色实例。

### 8.2 发动三连缺陷与关闭结果

修复前，`PrivateInvestigator_TripleDoesNotLeaveUsageBoundToConsumedMaterial` 稳定失败：已发动材料参与三连后，`RecruitActionStates` 仍指向被消耗的旧 `InstanceId`。根因不只在三连迁移缺失：旧状态仅以 `SourceInstanceId` 标识，而 `RecruitActionService` 又在 resolver commit 完成后才记账；若发动效果自身在 commit 中触发三连，旧来源已被消耗，服务仍会重新创建旧实例状态。

关闭实现如下：

- 状态身份提升为 `(SourceInstanceId, ActionId)`；旧存档的空 `ActionId` 仅在当前实例只有一个发动能力时兼容认领，避免变形或多能力串用次数。
- 执行服务在 resolver commit 前写入暂定使用状态；commit 抛错则回滚。这样三连发生在发动效果内部时，三连事务能看见并迁移本次使用，而不会在事务后复活旧来源状态。

### 8.6 战斗自然游标与伤害前进击时间链

真实酒馆语义固定为两条互相独立但必须一起验证的规则：

1. **自然攻击顺序以上一个自然攻击者的位置为锚点，不提前保存“下一位”身份，也不按新单位的裸索引跳转。** 某一方完成自然攻击声明时，只记录本次自然攻击者的 `InstanceId`、位置和稳定后继；等对方完整顶层攻击事务结束、该方再次选择自然攻击者前，才惰性解析旧锚点。锚点仍存活时从它当前右侧继续；锚点已离场且其死亡链产生单位时，由该链最左侧仍可攻击的产物接管原位置，创建顺序按亡语召唤先于复生；锚点离场且无产物时，从其空出位置顺延。与锚点无关的后排死亡、召唤或复生不得改变顺序；首轮无锚点时直接按当前棋盘选择，不伪造游标重定向事件；风怒和立即攻击只插队，不重置或消耗自然锚点。这里的结算边界不是单个 `DamageResolved`，而是下一次自然选攻前的稳定边界，因此同样覆盖伤害后死亡链和尚未造成伤害便取消的攻击。
2. **真实进击在碰撞伤害前完整结算。** 时间链为：锁定 attacker/defender → `AttackDeclared` → 进击效果 → 逐亡陆行鸟等真实攻击观察者 → 其产生的死亡、亡语、召唤与复生完整结算 → 按原 `InstanceId` 重新校验双方 → 碰撞伤害 → 伤害触发与死亡结算 → 推进自然游标。若伤害前链使原 attacker 或 defender 离场，旧碰撞取消，不得对离场对象继续造成伤害。目标型进击使用本次锁定的实际 defender，不能重新取敌方最左随从。

外部“触发进击”仍保持纯效果重放：天诞逃生飞龙发动、起义者之刃、进击饰品与黑暗之赐只结算进击效果；不产生 `AttackDeclared`、碰撞伤害或逐亡陆行鸟观察事件。
