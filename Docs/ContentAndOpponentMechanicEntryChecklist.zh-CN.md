# 卡牌与敌方机制准入清单

本清单用于后续批量补卡、敌方英雄技能、战斗开始法术和高级机制扩展。Phase 1–4 的稳定性与架构回归未通过时，不进入批量内容合入。

## 一、内容数据

- CardId、名称、类型、费用/酒馆等级、种族与来源池完整且唯一。
- 明确 `ImplementationStatus`、可提供状态和代理级别；未实现内容不能伪装为完整实现。
- 正式图片、分类占位图、程序占位视觉至少命中一级；缺图清单可审计。
- 图片展示模式明确采用 `Auto / Crop / Contain`，头像或紧凑构图不得被默认裁剪破坏。

## 二、机制注册

- 新增系统级能力时，在 `MechanicCoverageRegistry` 注册稳定键、配置入口、战斗消费、UI 可见性、测试状态和可信度。
- 卡牌级内容进入对应实现注册表或数据状态字段，不额外维护重复名单。
- 注册表校验必须保证稳定键、CardId、系统名称无重复，说明与可信度非空。

## 三、敌我双方一致性

- 明确机制属于玩家、敌方或双方；双方机制必须使用同一 `SideCombatModifierState` 语义。
- 全局成长通过 `SideModifierService` 映射、回算和持久化，不直接新增第二份影子字段。
- 复制、镜像、加载场景和战斗奖励结算后，已有战场/手牌/商店牌必须重新计算历史附魔。
- 敌方战斗开始法术遵循既有双方开战顺序，并验证一场战斗最多消费一次、未触发也不能跨回合保留。

## 四、场景与存档

- 新字段必须说明默认值和旧场景行为。
- 破坏兼容性的变更增加有序迁移步骤，不使用新的临时布尔开关代替版本迁移。
- `TestScenarioMapper.Capture` 和文件仓库保存必须输出当前场景版本。
- 至少覆盖旧版本迁移、当前版本直读、重复迁移幂等和未知未来版本拒绝。

## 五、测试准入

- 机制单元测试：效果、边界值、目标合法性、一次性消费。
- 双方一致性测试：玩家与敌方相同输入得到相同语义结果。
- 黑盒顺序测试：回合结束、战斗开始、双方触发、法术消费、战斗结束、下回合。
- UI 测试使用最小目录夹具；只有资源目录测试才加载完整 JSON 卡库。
- 禁止通过提高 NUnit 超时掩盖重复资源解析、整页重建或测试状态泄漏。
- 合入前运行相关测试类和完整 EditMode 回归，并记录总数、失败数和耗时。

## 六、完成定义

一项新卡牌或敌方机制只有同时满足以下条件才算完成：数据可发现、实现状态诚实、UI 可操作、敌我语义明确、场景可迁移、测试可重复、覆盖注册表可审计。
